`point_history` (every sample of every point) is a TimescaleDB hypertable with
**native columnar compression** (Baler#192). Raw history is compressed, never
downsampled: hunting detection, Cx and the building record need the actual
samples, years later.

## What is compressed, and how

TimescaleDB stores `point_history` in time chunks (7 days each unless
`BALER_HISTORY_CHUNK_INTERVAL` says otherwise, see
[below](#chunk-interval-and-compress_after-at-high-ingest-rates)). A compressed chunk holds its rows as batches of up to 1,000 samples per point:

- **segmented by `point_uri, unit, label`**: the point URI is stored once per
  batch instead of in every row and every primary-key entry. `unit` and `label`
  are constant per point, so they cost nothing extra. They're segment columns so
  that the point-label lookup (`read_point_labels`, which runs on every
  `/api/read` of points and every `hisRead` expression) filters batches
  without decompressing them.
- **ordered by `ts DESC`**: timestamps and values are delta-encoded within each
  batch.
- **everything else is a compressed column**, including the per-sample
  `quality` flag ([Sample quality](/quality)). It varies from sample to sample,
  so it doesn't belong in the segment columns. NULL (ok) costs almost nothing.
  The quality sweep only flags the last hour, which is still uncompressed. A
  flag written into an older, compressed range takes the slower write path
  described below.

The continuous aggregates (`point_history_5m`, `point_history_1h`) aren't
compressed. They're small.

Migration 0001 sets compression up (`baler/migrations/v0001_baseline.py`, see
[Schema migrations](/schema-migrations)): it enables it on a database that
doesn't have it and adds the policy, once, before any service starts.
`BALER_HISTORY_COMPRESS_AFTER` is a setting rather than schema, so it's kept in
step separately: the `migrate` service and each process, once at start
(`baler/timeseries.py`, `sync_settings`), compare the policy with the setting
in one catalog read and replace the policy only if it differs. That change
waits at most 5 seconds for its lock, so it never queues ingest behind a long
read; if it can't get it, the next process start tries again. A failure there
is logged and never stops the process.

## When

A background job, added with `add_compression_policy`, compresses each chunk
once **all** of it is older than `BALER_HISTORY_COMPRESS_AFTER` (default
`7 days`). With 7-day chunks, raw data stays uncompressed for 7 to 14 days. The
job runs every 12 hours. A high-rate site shortens all three (next section but
two).

Why 7 days: data that arrives late should usually land in an uncompressed
chunk, because that path is the cheapest. Late data comes from:

- retained MQTT replays (seconds late);
- Windrow's trend-log backfill (hours late);
- an edge node's spool after an outage (a long weekend).

Writes into an already-compressed chunk **still work**. Inserts, upserts
(`ON CONFLICT ... DO UPDATE`, last write wins as always), `ON CONFLICT DO
NOTHING` replays and deletes all succeed. TimescaleDB decompresses only the
batches the write touches, and the policy recompresses the chunk on its next
run. `hisWrite` and `haystack_import` can write history of any age and take
this path. `tests/test_history_compression.py` covers all of these against the
pinned image.

One limit: by default one transaction may decompress at most 100,000 compressed
rows (`timescaledb.max_tuples_decompressed_per_dml_transaction`). An insert of a
*new* timestamp doesn't count against it, but an overwrite of an existing
`(point, ts)` decompresses that point's whole batch, up to 1,000 rows. Baler's
batched writers (`timeseries.write_point_values`: mqtt_listener, hisWrite,
haystack_import) lift the cap for their own transaction only (Baler#245). It
used to apply to them: a 2,000-point retained replay into compressed chunks
failed at 101,000 decompressed rows, and because mqtt_listener exits on a failed
batch and the broker redelivers it, ingest stopped in a restart loop. A listener
restart replays every retained reading, and a point quiet for longer than
`compress_after` has its retained reading in a compressed chunk, so the short
`compress_after` a large site wants would have made that routine.
`tests/test_history_chunks.py` writes a batch like that (2,000 points, each
overwriting a row and adding a new one) into compressed chunks.

A bulk SQL load of your own that rewrites a large old range in **one**
statement or transaction should decompress the chunk first (below), or `SET
timescaledb.max_tuples_decompressed_per_dml_transaction = 0` for that session.

## Chunk interval and `compress_after` at high ingest rates

Three settings decide how much history sits uncompressed (the "hot window"):

> hot window ≈ `compress_after` + one chunk interval + the policy's schedule (+ how long a run takes)

| Setting | Blank (default) | What it does |
|---|---|---|
| `BALER_HISTORY_CHUNK_INTERVAL` | left as it is: **7 days** on every install so far | length of each **new** chunk |
| `BALER_HISTORY_COMPRESS_AFTER` | 7 days | a chunk compresses once all of it is older than this |
| `BALER_HISTORY_COMPRESS_SCHEDULE` | half a chunk (12 h from 1-day chunks up) once the chunk interval is set; otherwise left as it is (12 h) | how often the compression policy runs |

All three are settings, not schema. Like `compress_after`, the `migrate` service
and each process compare them with the database once at start
(`baler/history_chunks.py`, called from `timeseries.sync_settings`) and change
only what differs, waiting at most 5 s for the lock. `python -m
baler.history_chunks status` shows what the database has now.

They're not a migration on purpose: a migration means the same thing on every
database forever, and these are per deployment. Nothing they run reads history:
`set_chunk_time_interval` and `alter_job` update one catalog row each, and the
policy swap is two catalog calls, so the cost doesn't grow with history.
Measured on a database with 6.5 M rows in 251 chunks, 248 of them compressed:
the check alone 2–4 ms, changing the interval and the schedule 6–15 ms,
replacing the policy for a new `compress_after` 9 ms, and the same change with
a long read holding the hypertable open in another session 15 ms (it doesn't
wait for readers; a concurrent write right after took 4 ms).

**A small site sets nothing.** 50 points every 5 s is 10 rows/s: a 7-day chunk
is about 1.5 GB raw, and its behaviour is exactly what it was before these
settings existed.

**A large one needs hours, not days.** At 100,000 points every 5 s (20,000
rows/s, about 250 B a row raw) a 7-day chunk would be about 3 TB, written for a
week before any of it compresses, and a compression run over it would take
days. The sizing rule (Baler#245): one chunk plus its indexes in about 25% of
Postgres' memory, `compress_after` a few chunk intervals, and the policy run
about every half chunk. `recommend` applies it:

```bash
python -m baler.history_chunks recommend --points 100000 --pg-memory 32g
# 20,000 rows/s, 32.0 GB for Postgres, 250 B/row raw
# chunk 1 hour ~18.00 GB raw; compress after 3 hours; policy every 30 minutes; hot window up to ~81.0 GB raw
# note: even a 1-hour chunk (18.0 GB) is over 25% of 32.0 GB: more memory for Postgres, or a narrower row (#245), before shorter chunks
BALER_HISTORY_CHUNK_INTERVAL=1 hour
BALER_HISTORY_COMPRESS_AFTER=3 hours
BALER_HISTORY_COMPRESS_SCHEDULE=
```

It never goes below 1-hour chunks: shorter ones multiply the chunk count (8,760
a year at 1 hour already), which every query plan pays for. Past that point the
row has to get narrower (`point_id int` instead of the URI text, #245's last
step), not the chunks shorter.

What a short `compress_after` costs: Windrow's trend backfill (hours late) and
an edge node's spool replay land in compressed chunks. That works (above), it's
just the slower write path. `ladder.py soak` writes both kinds into compressed
chunks during every soak and checks each row landed once.

**Changing the chunk interval never rewrites a chunk.** `set_chunk_time_interval`
applies to chunks created after it: the chunk open at the time keeps its range,
and the new length starts at its end. Rows keep landing in the old chunk until
then.

### Moving a live install to short chunks

On nash-srv (13 M+ rows, compressed 7-day chunks, `BALER_HISTORY_COMPRESS_AFTER`
already in `~/.config/baler/nash-srv.env`):

1. Deploying this code changes nothing on its own: with the chunk settings blank
   the database is left exactly as it is (`status` shows 7-day chunks, the policy
   every 12 h).
2. Size it: `python -m baler.history_chunks recommend --points <expected points>
   --pg-memory <what Postgres gets>`.
3. Put the result in `nash-srv.env` (for example `BALER_HISTORY_CHUNK_INTERVAL=1
   hour`, `BALER_HISTORY_COMPRESS_AFTER=3 hours`) and deploy. The `migrate`
   service applies it before any service starts; check with `docker compose run
   --rm migrate python -m baler.history_chunks status`.
4. What happens next:
   - the open 7-day chunk stays 7 days and takes rows until its end; 1-hour
     chunks start there;
   - on its next run (within 30 minutes) the policy compresses every
     uncompressed chunk whose end is more than 3 hours ago: on nash-srv that's
     the previous week's 7-day chunk, if it isn't compressed already. At
     the measured ~33,000 rows/s on the 1-CPU box, 22 M rows take about 11
     minutes, in one background worker (one CPU) while ingest carries on.
     Compression needs no extra disk beyond the compressed copy, and frees the
     uncompressed chunk at the end;
   - the open 7-day chunk compresses 3 hours after its end, the same way; after
     that every chunk is an hour long and compresses 3 to 4 hours after it closes.
5. To go back, set the values explicitly (`BALER_HISTORY_CHUNK_INTERVAL=7 days`,
   `BALER_HISTORY_COMPRESS_AFTER=7 days`): blank means "leave it as it is",
   not "put back 7 days". Chunks already made keep their length either way.

Measured results, the long soak that proves the hot window plateaus, and
compression throughput are on [Scale test](/scale-test#long-soak-disk-and-compression-245).

## What it saves

Measured on local stacks seeded by `scripts/seed_perf.py` (synthetic values
with random noise):

| Seed | Uncompressed | Compressed | Bytes per sample |
|---|---|---|---|
| 766 points every 10 s, 3,290,400 rows | 733 MB (heap 284 + indexes 449) | 26.8 MB | 222.8 → 8.2 |
| the same 12 h, plus 27 points every 5 s for 21 days: 13,123,304 rows | 2,878 MB | 105 MB | 219.3 → 8.0 |
| the same 13.1 M rows with #183's `quality` column, 0.1% flagged | 2,889 MB | 106 MB | 220.2 → 8.07 |

That's about 27× smaller. Real values compress differently: random noise in
every float is close to the worst case, while quantized sensor readings and
constant setpoints compress better. Irregular timestamps compress slightly
worse. For the live number, run the queries below on that install.

Reads return identical results either way. Compressed history is faster to
scan in bulk (a raw rollup or Cx availability over many points). The newest
chunks are always uncompressed, so current values and today's reads don't
change.

## Per-point probes on compressed chunks

curVal, hisStart and the Cx "latest as of" checks look up one row per point
(`timeseries.probe_points`). On uncompressed chunks they use #237's form: one
primary-key probe per chunk, which never walks a chunk's `ts` index. That form
asks *every* chunk, though, and on a compressed chunk each answer costs a sort
of the point's compressed batches, about 20 ms per chunk per point. So the
probe is split where the compressed chunks end:

- **Below that point** the plain `ORDER BY ts` probe runs. It stops at the
  first chunk with a row (about 0.2 ms per point), and compressed chunks have
  no full-size `ts` index to walk.
- **Above it** #237's form runs, over the uncompressed chunks only.
- **Order:** the side nearest the answer goes first (newest rows for curVal,
  oldest for hisStart). Only points it didn't find go to the other side.

The rows are the same as a single probe's. Measured on the 13.1 M-row seed
with the two oldest chunks compressed (what the policy compresses there),
curVal for the 27 deep-history points took 757 ms with #237's form alone and
2.8 ms split, against 1.5 ms with nothing compressed. hisStart took 77 ms
and 2.2 ms. Finding where the compressed chunks end costs a few milliseconds per
call.

Cx's empty-rows index (`point_history_empty`, built per chunk in the
background by commissioning_api) builds fine with compressed chunks present.
On a compressed chunk the index covers only rows written since compression,
and TimescaleDB reads the compressed rows directly, so the report's results
are the same either way (tested).

## Checking it

```sql
-- is it on, and what's the policy?
SELECT compression_enabled FROM timescaledb_information.hypertables
WHERE hypertable_name = 'point_history';
SELECT job_id, schedule_interval, config, next_start
FROM timescaledb_information.jobs j JOIN timescaledb_information.job_stats USING (job_id)
WHERE j.proc_name = 'policy_compression';

-- bytes before/after, and per sample
SELECT pg_size_pretty(before_compression_total_bytes) AS before,
       pg_size_pretty(after_compression_total_bytes) AS after,
       round(before_compression_total_bytes::numeric / NULLIF(after_compression_total_bytes, 0), 1) AS ratio
FROM hypertable_compression_stats('point_history');
SELECT round(hypertable_size('point_history')::numeric / (SELECT count(*) FROM point_history), 1) AS bytes_per_sample;

-- per chunk
SELECT c.chunk_name, c.range_start, c.range_end, c.is_compressed, pg_size_pretty(d.total_bytes)
FROM timescaledb_information.chunks c
JOIN chunks_detailed_size('point_history') d USING (chunk_name)
WHERE c.hypertable_name = 'point_history' ORDER BY c.range_start;
```

From the host: `docker compose exec postgres psql -U baler -c '...'` (or `-U
timberdoodle` on a legacy install).

## Changing `compress_after`

Set `BALER_HISTORY_COMPRESS_AFTER` in `.env` to any Postgres interval (`3
days`, `2 weeks`), then `docker compose up -d` so the services pick it up. The
first service to open a new history connection replaces the policy. Check the
`config` column above. An invalid interval is logged as an error, and the
current policy stays as it is.

A shorter interval saves disk sooner, but sends more late data down the slower
path. A longer one keeps more raw rows uncompressed.

To compress or decompress by hand, for example before a bulk rewrite of an old
range:

```sql
SELECT compress_chunk(c, if_not_compressed => true)
FROM show_chunks('point_history', older_than => now() - interval '7 days') c;
SELECT decompress_chunk(c, if_compressed => true)
FROM show_chunks('point_history', newer_than => '2026-01-01', older_than => '2026-02-01') c;
```

Turning compression off entirely means decompressing every chunk, which needs
the uncompressed disk space back. Then `SELECT
remove_compression_policy('point_history')` and `ALTER TABLE point_history SET
(timescaledb.compress = false)`. A service that starts afterwards turns
compression back on, so this is a manual, unsupported state.
