---
title: Scale test (how far one server goes)
---

`scripts/scale/` measures Baler's real ceiling on one server, toward **1,000,000 points each
reporting every 5 s** (200,000 readings/s). It is the harness for epic
[#190](https://github.com/jacobnash/Baler/issues/190). The deliverable is a measured ceiling and
the reason each step stopped, not a promise that 1M points fit on one box.

A step passes only if Baler **doesn't choke**, which means three things:

1. **No data loss.** Everything the broker acknowledged is stored (at least 99%), with no
   growing backlog and no broker drops.
2. **Responsive.** The UI/API read probes stay inside the [#178](https://github.com/jacobnash/Baler/issues/178)
   budgets while the load runs.
3. **Graceful under overload.** No container restarts or OOM kills, and lag stays visible
   rather than turning into a crash.

A step can also stop for a reason that is **not** a Baler ceiling, and the result says so
(`inconclusive`). That happens when the generator couldn't offer the rate, the live install on
the same host slowed down (live-safety), or the host disk ran low.

## What it runs

- **`loadgen.py`** simulates N points over real MQTT, in exactly the envelope Windrow publishes
  (`windrow/mqtt_sink.py`): `{"point", "value", "ts"}` with QoS 1, retained. It sends each
  equip's `{prefix}/equip/tags` (`{"tags", "points"}` as a JSON string) and every point's
  `{prefix}/{label}/tags` first, so the graph grows the way it does for real equipment. Then it
  sends readings for every point once per `--interval`, spread evenly across the interval. The
  topics are `fbf/scale/s<site>/e<equip>/<label>`. It runs `--procs` processes and measures
  itself: messages published, messages the broker acknowledged per second, and how far it
  falls behind schedule.
- **`ladder.py`** steps through the point counts. For each step it:
  1. publishes tags for the new points and waits for them to reach Oxigraph;
  2. runs readings for a warm-up (60 s), then a soak (15 min by default), sampling every 15 s;
  3. runs the read probes and a Cx run and report, still under load;
  4. stops the generator, waits for the lag canaries to drain, and compares what was stored
     with what the broker acknowledged, second by second;
  5. applies the pass conditions and writes the JSON result.

  It stops at the first step that doesn't pass, unless `--continue-on-fail` is given.
- **`compose.scale.yml`** is the override that makes the stack isolated (see below).
- **`budgets.json`** holds the read probes and their budgets. The ones marked `#178` come from
  that issue; the `provisional` ones have no #178 budget yet.

Steps default to 10k, 25k, 50k, 100k, 250k, 500k and 1M. On a host with fewer than 4 CPUs
they start at 1k, 2.5k and 5k first. `--steps 10k,25k` picks your own.

## Isolation (never touches live)

The scale stack is its own compose project, `-p scale`, with these differences from live.
(`SCALE_PROJECT=scale2` runs a second, separately named one beside it, with project, volume
prefix and env file `scripts/scale/scale2.env` all following that name. The name must contain
`scale`.)

- volumes `scale_*` (`BALER_VOLUME_PREFIX=scale`);
- every port moved off the live defaults onto `127.0.0.1` (`SCALE_*_PORT`; the defaults are
  2xxxx, e.g. gateway 28080 and broker 21883);
- its own secrets, and its own broker account (`scalegen`), in `scripts/scale/scale.env`,
  which `ladder.py init` generates (mode 600, git-ignored).

Before `up`, `run`, `crash` or `down`, `ladder.py` reads the effective `docker compose config`
and **refuses** to continue if any of these hold:

- the project is a live name (`baler`, `baler-deploy`, `timberdoodle`, …) or the checkout's
  directory name;
- any volume falls outside `scale_`;
- any published port is a live default (1883, 8883, 7878, 5433, 16686, 4318, 3033, 8080, 8888,
  8011, 47808, 47900);
- the env file is the checkout's `.env`.

`up` also refuses if another stack already holds the scale ports, and checks that one reading
published as `scalegen` really reaches `point_history`. That check matters because mosquitto
acknowledges publishes its ACL denies.

**Resource caps.** Every scale container has a `cpus` and `mem_limit` (`SCALE_CPUS_<SERVICE>`,
`SCALE_MEM_<SERVICE>`; the defaults are in `compose.scale.yml`, e.g. postgres 2 CPUs / 6 GB and
mqtt_listener 1 CPU / 1 GB). `ladder.py` clamps CPU caps to the host's CPU count, because Docker
refuses a cap above it. `SCALE_CPUSET=2-5` pins the whole stack to some host CPUs. Each
container's log is capped at 3 × 50 MB, because postgres runs with `log_statement=all`.
Everything else (images, commands, Postgres settings, durability) is exactly what
`docker-compose.yml` runs.

**Live-safety.** During a soak the ladder probes the live gateway with a cheap, read-only,
unauthenticated GET (`--live-url`, default `http://127.0.0.1:8080/ui/`) and watches the host
load average. It trips after 3 bad samples in a row, where bad means either:

- live latency above 3× its pre-run baseline (and at least 0.5 s over it); or
- load per CPU above 1.5× its baseline (and at least 2).

The step then stops and is marked `inconclusive: live-safety`, never a Baler ceiling. Tune it
with `--live-latency-factor` and `--live-load-factor`.

## Running it on nash-srv

Use a **separate checkout** of the branch, never `~/baler-deploy`:

```sh
git clone https://github.com/jacobnash/Baler.git ~/baler-scale
cd ~/baler-scale && git checkout claude/scale-harness   # or main, once merged
python3 -m venv ~/.venv-scale && ~/.venv-scale/bin/pip install -e .
PY=~/.venv-scale/bin/python

$PY scripts/scale/ladder.py init     # scripts/scale/scale.env, fresh secrets
$PY scripts/scale/ladder.py guard    # prints project, volumes and ports, or refuses
$PY scripts/scale/ladder.py up       # builds and starts the scale stack (5-10 min the first time)

# The ladder. nash-srv sees 1 CPU today, so the steps start at 1k. Run it detached:
nohup $PY scripts/scale/ladder.py run --no-up --procs 1 > ~/scale-ladder.log 2>&1 &
tail -f ~/scale-ladder.log

# Durability: kill -9 the listener, then postgres, mid-run; count acknowledged readings lost
$PY scripts/scale/ladder.py crash --points 5000 --procs 1

$PY scripts/scale/ladder.py table scripts/scale/results/*-ladder.json   # rows for the table below
$PY scripts/scale/ladder.py down --rmi                                  # remove the stack, volumes, images
```

A ladder starts on a **clean** stack: the read probes scale with every point in the graph, so
`run` refuses when the graph already has more scale points than the first step. To run it again,
`down` then `up` first (`crash` reuses whatever is there, so run it after the ladder).

Copy the result JSON files (`scripts/scale/results/<run-id>-ladder.json`) somewhere that
outlives the checkout. Every result records:

- the hardware: `nproc`, CPU model, the CPU affinity the run had, RAM, disk free, load at start;
- the Baler and Windrow commits;
- the Postgres durability settings, read live;
- the CPU caps and cpuset;
- the full command.

So a 1-CPU run and a 12-CPU run are never compared without saying so.

## What each metric means

| Metric | Where it comes from | Meaning |
|---|---|---|
| `generator.achieved_rps`, `offered_ratio` | the generator's own PUBACK counts | What was actually offered. Below 99% of the target, the step is `inconclusive` (a generator limit). |
| `ingest.acked` / `stored` / `stored_ratio` | PUBACKs per second of payload `ts` vs. `point_history` rows with `ts` in the same seconds | **Data loss.** Must be ≥ 99%. |
| `ingest.stored_rps`, `stored_rate_ratio` | delta of `pg_stat_user_tables` inserts+updates on `point_history`'s chunks over the soak | Sustained write rate, independent of row timestamps. |
| `ingest.stored_rps_per_host_cpu` | `stored_rps / nproc` | Comparable across machines. |
| `ingest.broker_dropped_delta` | `$SYS/broker/publish/messages/dropped` | Deliveries mosquitto dropped because a subscriber's queue was full. It's broker-wide: if readings are missing it was the listener (data loss); if stored = acked, it was another subscriber. (Before #243 that meant fault_detector or derivation_engine, whose QoS 0 subscriptions silently missed readings. They now read the reading feed instead.) Must be 0. |
| `lag.p50_s` / `p95_s` / `max_s` | canary reading every 2 s on `fbf/scale/canary/lag`, polled in `point_history` | **End-to-end lag**, publish to row stored, behind the same queue as the load. p95 must be under 30 s. |
| `lag.first_third_median_s` → `last_third_median_s` | same | **Backlog growth.** Rising by more than 10 s over the soak fails the step. |
| `lag.lost` | canaries never stored within 300 s | Lost data. |
| `broker.*` | `$SYS/#` | Messages in/out, store count/bytes (queued + retained), load per minute, heap. |
| `resources.<service>` | `docker stats` every sample | CPU % (100 = one core), memory against the cap, block I/O. |
| `containers.<service>` | `docker inspect` | Restarts during the step, OOM kills, exit status. Any restart fails the step. |
| `samples[].pg_roundtrip_s` | `SELECT 1` timed | Postgres responsiveness under load. |
| `db.*` | `hypertable_detailed_size`, `approximate_row_count`, `timescaledb_information` | Chunks and chunk interval, table/index bytes, **bytes per row**, database size. Once a compression policy exists (#192), also `db.compression`: bytes before and after compression and the number of compressed chunks, so compressed and uncompressed bytes per row sit side by side. Raw history is never downsampled: compression only. |
| `db.bytes_per_day_raw_at_this_rate`, `ingest.rows_per_day_at_this_rate` | bytes/row × stored rows/s × 86,400 | **Disk-growth math** at the rate measured. |
| `graph.ingest_s`, `tags_per_s` | Oxigraph count of `scale` points after publishing a step's tags | How long the graph takes to absorb new equipment. |
| `graph.triples`, `count_*_s` | SPARQL `COUNT` timed | Graph size and the time of a full scan. |
| `probes[]` | timed GETs through the gateway as the test org's admin, 5 runs, warm median vs. `budgets.json` | **Responsiveness.** Any probe over budget, or not HTTP 200, fails the step. |
| `rules.<service>.median_cycle_s` | `service_heartbeats` beat-to-beat | Fault detector and derivation engine cycle time, including their sleep (30 s and 10 s by default). Since #243 their reading-feed threads beat too (every 10 s), so this is the beat interval; the His sweep's own duration is `heartbeat.his.sweep_s`. |
| `rules.<service>.feed` | `reading_feed_consumers` sampled every 15 s | **Rule-daemon misses and lag** (#243). `missed_readings_delta` counts readings pruned from the feed before the daemon read them (more than `BALER_FEED_RETENTION_S` behind) and must be 0. `lag_s_max`/`lag_s_last` show how far behind it ran; still over 30 s at the end of the soak fails the step. |
| `rules.<service>.heartbeat` | `service_heartbeats.detail` | Readings consumed, Cur-mode evaluations (`cur_evaluations`) or rows run (`cur_rows`), and for fault_detector the last His sweep: `sweep_s`, rules, faulted points. |
| `cx_run_s` | creating a 1 h Cx run over site 0 (500 points) and waiting for it | Commissioning verification time. |
| `durability.comparable` | `SHOW fsync / synchronous_commit / full_page_writes` on the server **and** on an ingest-path connection (from inside the listener container) | `true` only if all three are on end to end. A non-durable run is never labelled comparable. |

The ladder adds two rules to the test org, so per-point rule load is realistic: a Cur-mode
`range` rule over every scale point, and a His-mode `stale` rule. Their bounds keep them
from firing, so a fault storm doesn't distort the run.

`crash` runs readings, kills each `--kill` service with `docker kill -s KILL` mid-run (default:
`mqtt_listener`, then `postgres`), brings it back, drains, and reports `missing_acked`. That is
the number of readings the broker acknowledged that never reached `point_history`. Batching
and group commit are fine; losing acknowledged readings is not.

## Long soak: disk and compression (#245)

The ladder's steps are 15 minutes long, too short for a compression cycle. `ladder.py soak` holds
one point count for hours and answers [#245](https://github.com/jacobnash/Baler/issues/245)'s
question: once compression keeps up, does `point_history`'s disk stop growing at the raw rate, and
do lag, reads, the continuous aggregates and late writes stay fine through compression cycles?

Set the chunking under test in the scale env file **before** `up`, so every service agrees on it
(each keeps the policy in step with its own environment at start, see
[History compression](/history-compression#chunk-interval-and-compress_after-at-high-ingest-rates)):

```sh
# scripts/scale/scale.env (or <SCALE_PROJECT>.env)
BALER_HISTORY_CHUNK_INTERVAL=1 hour
BALER_HISTORY_COMPRESS_AFTER=3 hours
```

`soak` refuses to run on 7-day chunks unless `--allow-default-chunks` is given. It then runs the
generator at `--points` for `--duration` seconds (default 6 h) and records:

| Every | What | From |
|---|---|---|
| `--sample-every` (30 s) | disk: `point_history` total, **hot** (uncompressed chunks) and compressed bytes and chunk counts, before/after compression bytes, WAL, database | `chunks_detailed_size`, `hypertable_compression_stats`, `pg_ls_waldir` |
| | the oldest uncompressed chunk's age past its end, and the **backlog** (chunks old enough to compress that aren't yet) | `timescaledb_information.chunks` |
| | each compression run: duration, chunks, rows (the chunks' inserts while hot), **rows/s** | `job_stats`, `pg_stat_user_tables` |
| | whether a compression run is in progress (polled every 2 s) | `pg_stat_activity` |
| | the 5m/1h aggregates' watermark age; canary lag; restarts | catalog, canary, `docker inspect` |
| `--probe-every` (600 s) | every read probe in `budgets.json` plus its `soak_probes`: history over the last hour and across the hot/compressed boundary, `hisRead(pastWeek)` for 100 and 1,000 points. Rounds that overlapped a compression run are marked | gateway |
| `--late-every` (1800 s) | late data into the newest compressed chunk, over MQTT at the soak's own rate: every point's reading there **replayed** (same ts, new value: a spool or retained replay) and a new reading **backfilled** 1.23 s after it (Windrow's trend backfill). Then each must be stored exactly once, with the new value | generator account |

At the end it compares stored with acknowledged readings over the soak (minus its own backfill),
checks `point_history_5m` against the raw fold over the newest compressed hour, and writes
`results/<run>-soak.json`. `summary` holds the numbers; `status`/`reasons` the verdict.

**Pass** needs all of these (`soak.evaluate_soak`, tested in `tests/test_scale_soak.py`). The
steady phase starts after `compress_after` + 2 chunks + one schedule:

- **Hot window bounded:** hot bytes in the second half of the steady phase at most 1.25× the
  first half's; no chunk uncompressed longer past its end than `compress_after` + chunk + 2 ×
  schedule + the longest run; the backlog not growing.
- **Disk grows at the compressed rate:** total bytes per stored row, between two samples a whole
  number of chunk intervals apart (the same point of the hot sawtooth), at most 2× the measured
  compressed bytes per row.
- **Compression keeps up:** no failed run. `compression_margin` reports median compression rows/s
  over ingest rows/s (one background worker).
- **Ingest:** ≥ 99% stored, no lost canaries, p95 lag under 30 s overall and in the samples taken
  during compression, no growing backlog, no restarts.
- **Reads:** every probe round in budget, and at least one round during a compression run
  (otherwise `inconclusive`).
- **Aggregates:** the 5-minute aggregate equals the raw fold over a compressed hour; watermarks no
  further behind than their offset plus two schedules (20 min for 5m, 2 h 10 min for 1h).
- **Late data:** at least one late round, every replay and backfill stored once.
- At least 2 chunk intervals and 2 compression cycles in the steady phase, or the verdict is
  `inconclusive: soak too short`.

On nash-srv, the real one (6 h at 100k points, after `init`):

```sh
cd ~/baler-scale && git pull
PY=~/.venv-scale/bin/python
$PY -m baler.history_chunks recommend --points 100000 --pg-memory 6g   # the scale stack's postgres cap
printf 'BALER_HISTORY_CHUNK_INTERVAL=1 hour\nBALER_HISTORY_COMPRESS_AFTER=3 hours\n' >> scripts/scale/scale.env
$PY scripts/scale/ladder.py down && $PY scripts/scale/ladder.py up
nohup $PY scripts/scale/ladder.py soak --no-up --points 100000 --duration 21600 --procs 4 \
  --sample-every 60 --probe-every 900 --late-every 3600 > ~/scale-soak.log 2>&1 &
tail -f ~/scale-soak.log
```

Disk at 100k: about 18 GB raw per 1-hour chunk and a hot window up to about 80 GB, plus about
9 GB/day compressed at 5 B/row. Keep `--min-free-gb` (default 5) where it is; the soak stops
(`inconclusive`) rather than fill the disk. Raise `SCALE_MEM_POSTGRES` if the box has the
memory: the sizing rule wants a chunk in 25% of it.

**Highest passing step: 2,500 points.** Ingest itself held up through 25,000 points: 100% of
acknowledged readings were stored, zero lost canaries, and p95 lag stayed under 30 s at every step.

**First bottleneck, before the fixes: ingest.** The listener did one INSERT round trip per
reading, latency-bound at about 1,000 readings/s and about half a CPU. Past that, mosquitto's
per-session queue overflowed and readings were dropped.

**First bottleneck, after the fixes: reads.** Every list grows with the total number of
points: `read?filter=point` is unpaged, `readAll(equip)` folds raw history, and the Cx report
grows with history ([#244](https://github.com/jacobnash/Baler/issues/244)).

**Next, at 25k points: the rule daemons.** `fault_detector` and `derivation_engine` took every
reading over QoS 0, fell behind (cycle times of 81 s and 121 s) and silently missed readings
([#243](https://github.com/jacobnash/Baler/issues/243)). Fixed since: see
[Rule daemons on the reading feed](#rule-daemons-on-the-reading-feed-243) below.

The listener's own ceiling wasn't reached locally: it used 31% CPU at 5,040 readings/s.

**With the read fixes** ([#244](https://github.com/jacobnash/Baler/issues/244)). Same VM, steps,
soak (300 s) and caps, on a clean stack each time. Run `20261108T165606Z` is main at `6946378`
(load average 1.3 at start); run `20261108T180642Z` is the fixes (load average 6.0 at start: other
stacks shared the VM, so its 2.5k column is no faster than before).

| 2,500 | before | pass | 0.66 s | 0.07 s | 0.69 s | 0.32 s | - |
| 2,500 | after | pass | 0.80 s | 0.09 s | 0.55 s | 0.28 s | - |
| 5,000 | before | fail | 1.74 s | 0.22 s | 1.62 s | 0.48 s | read?filter=point |

**Highest passing step, with the read fixes: 5,000 points.** At 10k, read?filter=point and
readAll(equip) still miss. Both return every point, so they grow with the graph by definition.
What's left is the per-request pull of every record's triples out of Oxigraph (about 3.5 µs a
triple, 136k triples at 10k points) and the encode.

Most of the time was spent in reading and decoding the graph, not in Postgres:

- Graph reads that pull every record's triples (haystack `build_records`, hisquery
  `describe_points`) use SPARQL TSV, decoded row by row as Oxigraph streams it. That's half the
  bytes of JSON results and half of Oxigraph's own time.
- A filter that is only or'ed tags (`point`, `equip`, `ahu or vav`) is answered by the union of its
  leaf sets. It skips the flag joins and the join on every candidate's triples: `point` at 10k
  points dropped from 0.6 s to 0.2 s.
- Each API freezes its startup heap after warm-up (`gc.freeze`), so the cyclic GC stops re-walking
  the vendored Brick and the lookup tables during every large read. A 10k-point read went from
  1.78 s to 1.07 s in-process.
- The Cx inventory reads equipment and points with two plain scans instead of one UNION/OPTIONAL
  over every typed subject: 0.35–0.47 s down to 0.14 s at 10k points.
- `hisRead` reads the points' graph metadata on a side thread while Postgres folds their history.

first request after restart and warm-up, warm is the median of the next 5):

### Rule daemons on the reading feed (#243)

Same dev VM (4 vCPU), quieter this time: no other stacks running. Soak 300 s, clean stack,
compose project `scale243` (`SCALE_PROJECT`). Before is main at `4f5b4ce` (run
`20261108T192647Z`), after is this change (run `20261108T201511Z`).

| | 10k before | 10k after | 25k before | 25k after |
|---|---|---|---|---|
| Readings the rule daemons missed | not counted | **0** (counted) | not counted | **0** (counted) |
| Rule daemons' lag behind storage, max | unknown | 0.16 s / 0.24 s | unknown | 0.28 s / 0.28 s |
| fault_detector CPU, mean | 37.0% | **1.0%** | 61.6% | **5.3%** |
| derivation_engine CPU, mean | 25.5% | 4.0% | 46.5% | 13.8% |
| fault_detector His cycle (interval 30 s) | 38.2 s | sweep 0.29 s | 77.4 s | sweep **0.80 s** |
| derivation_engine tick (5 s) | 20.0 s | 18.1 s ¹ | 109.1 s | 18.6 s ¹ |
| mqtt_listener CPU | 19.8% | 17.5% | 33.2% | 35.4% |
| postgres CPU | 18.6% | 16.8% | 32.3% | 37.4% |
| mosquitto CPU | 10.3% | 7.7% | 16.4% | 14.2% |
| Broker drops | 0 | 0 | 0 ² | 0 |

¹ The beat-to-beat median: both daemons now beat from their feed thread every 10 s as well, so
this no longer measures a cycle. ² This quiet run happened to drop nothing. The first local
run (above) dropped 115,903 deliveries to the rule daemons at 25k, and nothing in Baler could
tell you either way. That is the point of the change.

- **No QoS 0 subscriptions left.** Both daemons read `reading_feed`, so the broker fans each
  reading out to the listener only. The listener appends each committed batch to the feed in
  the same transaction. That's one more INSERT per batch, built server-side from the staging
  table: about 5 points of Postgres CPU at 25k, including `point_registry` upkeep and the
  daemons' reads.
- **fault_detector is idle-cheap.** At 25k it evaluated 3.9M Cur-mode rule checks in the soak,
  a dict lookup each. The His sweep (one `GROUP BY` per stuck window, registry candidates for
  stale) took 0.8 s, against 77 s before.
- **Misses are visible.** Checked live: with `BALER_FEED_RETENTION_S=20`, `fault_detector`
  was stopped for 60 s at 2,000 readings/s. The listener logged `fault_detector MISSED …`
  per prune, and `reading_feed_consumers` counted 80,840 readings in 137 batches. The
  Fault detection card on `/ops/status` went degraded ("missed 80840 reading(s)…").
- **The next wall in fault_detector is the quality sweep** ([#183](https://github.com/jacobnash/Baler/issues/183)'s
  range/spike/unit checks). Every 5 minutes it re-judges the last hour of every classified
  point in Python. At 25k it read 1.3M rows in 10.5 s; a 25k stack with a full hour of
  history read 2.2M rows in 13 s. That's about 72M rows an hour at 100k points, longer than
  its interval. It used to `fetchall` all of them at once, which OOM-killed the daemon
  (1 GB cap) once a full hour of 25k-point history existed. It now reads 150 points at a
  time, and its duration is in the heartbeat (`quality.sweep_s`), but it still has to become
  incremental.

Batched writes cost almost nothing to make durable. At 1,000-row batches, `synchronous_commit=on`
measured 17–25k rows/s against 15–21k for `off`; single-row writes pay the fsync (about 1.3×).

restart loop; writers now lift that cap per transaction

### Disk growth

At 1M points every 5 s, that's 200,000 rows/s, or 17.3 billion rows/day. Bytes per row comes
from `db.bytes_per_row` in each result (table plus index, uncompressed). On the first local
runs it was 228–265 B/row (241 at 1k points, 265 at 25k). That works out to about **4.2 TB/day
raw** at 1M points, which is why
native compression ([#192](https://github.com/jacobnash/Baler/issues/192), under [#221](https://github.com/jacobnash/Baler/issues/221)) and a narrower row matter. Raw rows are kept, never downsampled. Fill in compressed bytes per row from `db.compression` once #192 lands.
