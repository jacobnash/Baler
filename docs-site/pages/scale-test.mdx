---
title: Scale test (how far one server goes)
---

`scripts/scale/` measures Baler's real ceiling on one server, toward **1,000,000 points each
reporting every 5 s** (200,000 readings/s). It is the harness for epic
[#190](https://github.com/jacobnash/Baler/issues/190). The deliverable is a measured ceiling and
the reason each step stopped, not a promise that 1M points fit on one box.

A step passes only if Baler **doesn't choke**, which means three things:

1. **No data loss.** Everything the broker acknowledged is stored (at least 99%), with no
   growing backlog and no broker drops.
2. **Responsive.** The UI/API read probes stay inside the [#178](https://github.com/jacobnash/Baler/issues/178)
   budgets while the load runs.
3. **Graceful under overload.** No container restarts or OOM kills, and lag stays visible
   rather than turning into a crash.

A step can also stop for a reason that is **not** a Baler ceiling, and the result says so
(`inconclusive`). That happens when the generator couldn't offer the rate, the live install on
the same host slowed down (live-safety), or the disk holding Docker's data ran low.

The point count is not the goal: the ladder exists to find bottlenecks. Every step, passing or
not, names what limited it (or, when it passed, what is closest to its limit next), with the
evidence captured while it ran.

## What it runs

- **`loadgen.py`** simulates N points over real MQTT, in exactly the envelope Windrow publishes
  (`windrow/mqtt_sink.py`): `{"point", "value", "ts"}` with QoS 1, retained. It sends each
  equip's `{prefix}/equip/tags` (`{"tags", "points"}` as a JSON string) and every point's
  `{prefix}/{label}/tags` first, so the graph grows the way it does for real equipment. Then it
  sends readings for every point once per `--interval`, spread evenly across the interval. The
  topics are `fbf/scale/s<site>/e<equip>/<label>`. It runs `--procs` processes and measures
  itself: messages published, messages the broker acknowledged per second, and how far it
  falls behind schedule.
- **`ladder.py`** steps through the point counts. For each step it:
  1. publishes tags for the new points and waits for them to reach Oxigraph;
  2. runs readings for a warm-up (60 s), then a soak (15 min by default), sampling every 15 s;
  3. runs the read probes and a Cx run and report, still under load;
  4. stops the generator, waits for the lag canaries to drain, and compares what was stored
     with what the broker acknowledged, second by second;
  5. applies the pass conditions, names the step's **limiter** from the evidence sampled during
     the soak (see [Reading the limiter](#reading-the-limiter-269)), and writes the JSON result.

  It stops at the first step that doesn't pass, unless `--continue-on-fail` is given.
- **`compose.scale.yml`** is the override that makes the stack isolated (see below).
- **`budgets.json`** holds the read probes and their budgets. The ones marked `#178` come from
  that issue; the `provisional` ones have no #178 budget yet.

Steps default to 10k, 25k, 50k, 100k, 250k, 500k and 1M. On a host with fewer than 4 CPUs
they start at 1k, 2.5k and 5k first. `--steps 10k,25k` picks your own.

## Isolation (never touches live)

The scale stack is its own compose project, `-p scale`, with these differences from live.
(`SCALE_PROJECT=scale2` runs a second, separately named one beside it, with project, volume
prefix and env file `scripts/scale/scale2.env` all following that name. The name must contain
`scale`.)

- volumes `scale_*` (`BALER_VOLUME_PREFIX=scale`);
- every port moved off the live defaults onto `127.0.0.1` (`SCALE_*_PORT`; the defaults are
  2xxxx, e.g. gateway 28080 and broker 21883);
- its own secrets, and its own broker account (`scalegen`), in `scripts/scale/scale.env`,
  which `ladder.py init` generates (mode 600, git-ignored).

Before `up`, `run`, `crash` or `down`, `ladder.py` reads the effective `docker compose config`
and **refuses** to continue if any of these hold:

- the project is a live name (`baler`, `baler-deploy`, `timberdoodle`, …) or the checkout's
  directory name;
- any volume falls outside `scale_`;
- any published port is a live default (1883, 8883, 7878, 5433, 16686, 4318, 3033, 8080, 8888,
  8011, 47808, 47900);
- the env file is the checkout's `.env`.

`up` also refuses if another stack already holds the scale ports, and checks that one reading
published as `scalegen` really reaches `point_history`. That check matters because mosquitto
acknowledges publishes its ACL denies.

**Resource caps.** Every scale container has a `cpus` and `mem_limit` (`SCALE_CPUS_<SERVICE>`,
`SCALE_MEM_<SERVICE>`; the defaults are in `compose.scale.yml`, e.g. postgres 2 CPUs / 6 GB and
mqtt_listener 1 CPU / 1 GB). `ladder.py` clamps CPU caps to the host's CPU count, because Docker
refuses a cap above it. `SCALE_CPUSET=2-5` pins the whole stack to some host CPUs. Each
container's log is capped at 3 × 50 MB, because postgres runs with `log_statement=all`.
Everything else (images, commands, Postgres settings, durability) is exactly what
`docker-compose.yml` runs.

**Live-safety.** During a soak the ladder probes the live gateway with a cheap, read-only,
unauthenticated GET (`--live-url`, default `http://127.0.0.1:8080/ui/`) and watches the host
load average. It trips after 3 bad samples in a row, where bad means either:

- live latency above 3× its pre-run baseline (and at least 0.5 s over it); or
- load per CPU above 1.5× its baseline (and at least 2).

The step then stops and is marked `inconclusive: live-safety`, never a Baler ceiling. Tune it
with `--live-latency-factor` and `--live-load-factor`.

## Running it on nash-srv

Use a **separate checkout** of the branch, never `~/baler-deploy`:

```sh
git clone https://github.com/jacobnash/Baler.git ~/baler-scale
cd ~/baler-scale && git checkout claude/scale-harness   # or main, once merged
python3 -m venv ~/.venv-scale && ~/.venv-scale/bin/pip install -e .
PY=~/.venv-scale/bin/python

$PY scripts/scale/ladder.py init     # scripts/scale/scale.env, fresh secrets
$PY scripts/scale/ladder.py guard    # prints project, volumes and ports, or refuses
$PY scripts/scale/ladder.py up       # builds and starts the scale stack (5-10 min the first time)

# The ladder. nash-srv sees 1 CPU today, so the steps start at 1k. Run it detached:
nohup $PY scripts/scale/ladder.py run --no-up --procs 1 > ~/scale-ladder.log 2>&1 &
tail -f ~/scale-ladder.log

# Durability: kill -9 the listener container, one listener worker, then postgres, mid-run;
# count acknowledged readings lost
$PY scripts/scale/ladder.py crash --points 5000 --procs 1

# Listener capacity alone (#233): readings/s with 1..4 worker processes, from a broker backlog
$PY scripts/scale/listener_bench.py --workers 1,2,3,4 --messages 300000

$PY scripts/scale/ladder.py table scripts/scale/results/*-ladder.json   # rows for the table below
$PY scripts/scale/ladder.py down --rmi                                  # remove the stack, volumes, images
```

A ladder starts on a **clean** stack: the read probes scale with every point in the graph, so
`run` refuses when the graph already has more scale points than the first step. To run it again,
`down` then `up` first (`crash` reuses whatever is there, so run it after the ladder).

Copy the result JSON files (`scripts/scale/results/<run-id>-ladder.json`) somewhere that
outlives the checkout. Every result records:

- the hardware: `nproc`, CPU model, the CPU affinity the run had, RAM, disk free, load at start;
- the Baler and Windrow commits;
- the Postgres durability settings, read live;
- the CPU caps and cpuset;
- the full command.

So a 1-CPU run and a 12-CPU run are never compared without saying so.

## Reading the limiter (#269)

Every step result has a `limiter`, `ladder.py run` prints it after each step and in its summary,
and `ladder.py table` has a column for it:

```
limiter per step:
      1,000  pass          none found; next: read?filter=point 0.21 s of 1.5 s (haystack.read.build_records 51%)
      5,000  fail          ingest listener: mqtt_listener CPU-capped (throttled 38%) [high]
max passing step: 1,000 points
```

`limiter.limiter` names the part that stopped the step and the number that says so.
`limiter.evidence` lists the symptoms (drops, lag, missed readings, slow probes) and then every
candidate part with how far past its threshold it ran (`[1.90x threshold]`). `limiter.also` lists
other parts that were also at their limit. `limiter.confidence` is:

- **high**: one part at its limit and the symptoms point at it;
- **medium**: several parts at their limit (the most saturated is named, the others are in
  `also`), or the cause was inferred from one side only, for example the listener writing all the
  time with nothing in Postgres to show why;
- **low**: there are symptoms but nothing was at its limit (`unattributed`). Something the
  sampler doesn't see is the limit. Look at `evidence.ticks` and the logs.

A step that passed has `limiter: "none found"` and a `next_suspect`: the part closest to its
limit, from `limiter.headroom` (every measured part, as a ratio to its threshold, highest
first). When a step passes, that is where the next step will most likely fail.

**The rules** (`scripts/scale/limiter.py`, tested on recorded samples in
`tests/test_scale_limiter.py`). They run in this order, and the first that applies names the limiter:

| # | When | Limiter |
|---|---|---|
| 1 | live-safety tripped; the Docker data root (DockerRootDir, not the checkout's disk) below `--min-free-gb`; the generator more than one interval behind schedule during the soak (`generator.behind_soak_max_s`), or offering under 99% of the target | `live-safety`, `disk space (…)`, `generator-bound (behind_s max 12.3 > 5 s, …)`. None of these is a Baler ceiling. |
| 2 | a container restarted or was OOM-killed; an mqtt_listener child restarted by its supervisor (#233) | `fault_detector OOM-killed (memory 99% of cap)`, `ingest listener: mqtt_listener worker-2 restarted 1x` |
| 3 | the graph didn't take a step's tags in time | `graph ingest (…)` |
| 4 | ingest symptoms: broker drops, < 99% stored, p95 lag ≥ 30 s or growing, lost canaries, listener queue past 80% of its cap, broker queue growing | the most saturated part of the ingest chain: `ingest listener: mqtt_listener CPU-capped (throttled 38%)`, `… CPU-bound (busiest thread 96% of a core)`, `broker: mosquitto …`, `postgres CPU-capped (…)`, `postgres write-bound (IO:WALSync 55%, …)`, `postgres locks (…)`, `disk (util p90 98%, 240 MB/s written)`; `broker drops (N; subscriber unattributed)` if none is at its limit |
| 5 | a rule daemon missed readings from the reading feed, or ended the soak > 30 s behind | `fault_detector behind on the reading feed: CPU-bound (…)` |
| 6 | a read probe over budget or not HTTP 200 | the worst probe (median / budget), the span that took most of its median request, and its API's CPU during the probes: `reads: read?filter=point (2.1 s > 1.5 s) haystack.encode 48%` |
| 7 | anything else `evaluate()` failed the step for | `unattributed: <reason>` |

A part is **at its limit** when it reaches its threshold (all of them are constants at the top of
`limiter.py`):

| Part | Threshold | From |
|---|---|---|
| A container's CPU cap | throttled in ≥ 20% of its CFS periods while its CPU p90 is ≥ 60% of the cap, or CPU p90 ≥ 90% of the cap | cgroup `cpu.stat` (`nr_throttled`/`nr_periods`) and CPU usage |
| One core (single-threaded services: the Python daemons and APIs, and mosquitto) | busiest thread ≥ 85% of a core, or one process ≥ 90% | `/proc/<pid>/task/*/stat` |
| Memory | peak ≥ 95% of the cap | cgroup memory minus inactive file cache, which is what `docker stats` shows |
| Disk (the device holding Docker's data root) | utilisation p90 ≥ 90% | `/proc/diskstats` `io_ticks` |
| Postgres waits | ≥ 40% of non-idle backend samples waiting on IO or WAL/buffer LWLocks, with at least 1 active backend per sample | `pg_stat_activity`, sampled every `--evidence-every` seconds |
| Postgres locks | ≥ 1 ungranted lock per sample on average | `pg_locks` |
| The listener's writer | inside `flush()` ≥ 80% of the time (per worker: the share averaged over them) | `mqtt_listener`'s heartbeat |

**With several listener workers (#233)** one core is each worker's limit, not the container's.
Each child runs as `python -m baler.mqtt_listener --child worker --index <n>` (or `--child tags`), so
the per-process figures name it: `ingest listener: mqtt_listener CPU-bound (worker 1 at 97% of a
core, 3 workers)` says that worker is GIL-bound and more workers would help, while `CPU-capped`
says the container's cap is the wall. Without per-process figures the container's CPU is divided
by the worker count. The supervisor's `mqtt_listener` heartbeat carries the workers' totals in the
shape a single listener's had (rows, `flush_s` summed with `writers`, the busiest worker's queue,
its peak and its cap), so the queue and writer rules read the same as before.

The threshold for throttling has a busy condition because a nearly idle API under a 0.25-CPU cap
is throttled in about 45% of its few CFS periods by its own healthcheck. Locally `auth_api`,
`derivation_api` and `validate_api` did exactly that at 4% CPU.

Consequences never outrank their cause. The listener writing all the time is explained by
anything else at its limit, and Postgres IO waits by a saturated disk. Each probe's limit is its
budget.

**What the sampler records.** `evidence.Sampler` runs from the end of the warm-up to the end of
the probes, every `--evidence-every` seconds (default 5). It reads files on the host and runs one
small Postgres query per tick, plus a few at each end of the step:

- `evidence.phases.soak` / `.probes`: per container, CPU (mean, p90) against its cap,
  throttled share and seconds, memory peak against its cap, and the busiest processes. Postgres
  backends are grouped by their process title (`postgres client baler`, `postgres:
  checkpointer`). Also the disk (utilisation, MB/s written, write await, free space on Docker's
  root), the broker (`queued` = `$SYS` store count minus retained, and drops per tick), Postgres
  (wait-event shares by backend type, lock waits) and the listener (queue depth and peak against
  its cap of 50,000, and its write-busy share).
- `evidence.pg_delta`: per-step deltas of `pg_stat_wal`, `pg_stat_bgwriter`, `pg_stat_io` (by
  backend type, object and context) and `pg_stat_database`. `evidence.pg_writes` summarises them
  (see the write gap below).
- `evidence.pg_top_statements`: `pg_stat_statements` top 10 by total time over the step. It is
  reset at the step's start, and loaded in the scale stack only (`compose.scale.yml`).
- `evidence.ticks`: every raw sample, so the verdict can be worked out again (or the rules
  changed and re-run) once the stack is gone.
- `evidence.overhead`: the sampler's own cost. That is its thread's CPU (`cpu_share_of_one_core`),
  wall time per tick, the time its Postgres queries took, and the time the ladder spent in
  `docker stats` (0 when the cgroups are readable: it is skipped then, because each call costs
  about 2 s of wall time and 0.2 CPU-s of dockerd).

The listener now writes a heartbeat (`service_heartbeats`, service `mqtt_listener`, every 5 s)
with `queue`, `queue_peak`, `queue_max`, `rows`, `batches` and `flush_s`, the seconds spent
writing. Without it the queue depth was only in a log line once a minute.

Each probe has a `trace`. The ladder pulls the probe's API spans from Jaeger for the probe's own
time window and works out each span's self time (its duration minus its children's). The
breakdown is the median over the probe's requests, against the median request
(`root_median_s`). `outside_spans_s` is the probe's median minus that: gateway, network, and
anything the API does outside a span.

**What it can't see.** On a host where Docker's cgroups aren't readable (rootless or remote
Docker), there's no per-container throttling, threads or memory. `resources` falls back to
`docker stats`, and verdicts that need those numbers come out `low` or `unattributed`. On cgroup
v1, per-container block I/O doesn't include buffered writes, so disk writes are judged at the
device. Device numbers include everything else on that disk, other stacks included.

### The Postgres write gap (875 GB of block writes)

At the end of the 100k step on nash-srv, `docker stats` showed 875 GB of block writes for
Postgres. `pg_stat_wal` stood at 17 GB after 50k, and the table plus indexes were 9 GB. Part of the
gap is how Docker counts, and part is real disk traffic:

1. **Counter effect: Docker's number is cumulative.** `docker stats` BlockIO counts from the
   container's start: every step before 100k, every graph phase and every probe round, not just
   the 100k soak. `pg_stat_wal` and the table size don't include the data pages Postgres rewrote
   along the way. On cgroup v2 Docker also sums `io.stat` over every device listed. On LVM or
   device-mapper storage, the same write can appear on the `dm-N` device and on the disk below it,
   which can double the count. Check with
   `cat /sys/fs/cgroup/system.slice/docker-<id>.scope/io.stat`.
2. **Real traffic: Postgres writes each row several times.** Measured locally at 5k points
   (1,017 rows/s, run `20261109T002820Z`, `evidence.pg_writes` and `pg_delta`). The window is the
   step's soak and probes, about 225 s and 229k stored rows:

   | Writes | Bytes | Per stored row |
   |---|---|---|
   | WAL (`pg_stat_wal.wal_bytes`, including 3,459 full-page images) | 134 MB | ~585 B |
   | New heap and index pages (`pg_stat_io`, client backend extends) | 50 MB | ~220 B |
   | The listener's TEMP staging table, `point_history_stage` (`temp relation` extends) | 30 MB | ~130 B |
   | Checkpointer page writes | 12 MB | ~55 B |
   | The stored row itself, table plus indexes (`db.bytes_per_row`) | | 225 B |

   That is about 4.4× the stored bytes. The ratio grows with the point count. `point_history` has
   three indexes led by `point_uri`, two of them substantial (the primary key and
   `point_history_labelled`), so every point's next reading goes to that point's own leaf page.
   At 100k points that is about 100k hot leaf pages per index, or roughly 1.6 GB for the two. The
   scale stack's `shared_buffers` is 1.5 GB: 25% of its 6 GB cap, which the image's tuning sets at
   init. So hot pages start being written out between touches, and every checkpoint is followed by a
   full-page image (8 kB of WAL) for each leaf's first change. With `max_wal_size` at 1 GB, those
   images alone fill the WAL quickly enough to *request* the next checkpoint. 240 MB/s at
   20,000 rows/s is 12 kB per row, about one page write plus one page of WAL per row. That fits
   this mechanism, and it is real disk traffic.

   This is an estimate from the 5k measurement plus the index arithmetic. The 100k step hasn't
   been re-run with the new evidence yet. When it is, `evidence.pg_writes` gives the answer
   directly: `checkpoints_requested` > 0, `wal_fpi` close to one per row, and
   `buffers_checkpoint` plus `buffers_backend` growing faster than rows confirm it. A step limited
   this way names `postgres write-bound (…)` or `disk (…)`, and its evidence lists the requested
   checkpoints. Levers, in order of cost: `max_wal_size` (fewer checkpoints means fewer full-page
   images), `wal_compression`, `shared_buffers`, and the row and index shape that #245 is changing.

## What each metric means

| Metric | Where it comes from | Meaning |
|---|---|---|
| `generator.achieved_rps`, `offered_ratio` | the generator's own PUBACK counts | What was actually offered. Below 99% of the target, the step is `inconclusive` (a generator limit). |
| `ingest.acked` / `stored` / `stored_ratio` | PUBACKs per second of payload `ts` vs. `point_history` rows with `ts` in the same seconds | **Data loss.** Must be ≥ 99%. |
| `ingest.stored_rps`, `stored_rate_ratio` | delta of `pg_stat_user_tables` inserts+updates on `point_history`'s chunks over the soak | Sustained write rate, independent of row timestamps. |
| `ingest.stored_rps_per_host_cpu` | `stored_rps / nproc` | Comparable across machines. |
| `ingest.broker_dropped_delta` | `$SYS/broker/publish/messages/dropped` | Deliveries mosquitto dropped because a subscriber's queue was full. It's broker-wide: if readings are missing it was the listener (data loss); if stored = acked, it was another subscriber. (Before #243 that meant fault_detector or derivation_engine, whose QoS 0 subscriptions silently missed readings. They now read the reading feed instead.) Must be 0. |
| `lag.p50_s` / `p95_s` / `max_s` | canary reading every 2 s on `fbf/scale/canary/lag`, polled in `point_history` | **End-to-end lag**, publish to row stored, behind the same queue as the load. p95 must be under 30 s. |
| `lag.first_third_median_s` → `last_third_median_s` | same | **Backlog growth.** Rising by more than 10 s over the soak fails the step. |
| `lag.lost` | canaries never stored within 300 s | Lost data. |
| `broker.*` | `$SYS/#` | Messages in/out, store count/bytes (queued + retained), load per minute, heap. |
| `resources.<service>` | the evidence sampler's cgroup reads (`docker stats` when cgroups aren't readable from the host) | CPU % (100 = one core) and memory against the cap. |
| `containers.<service>` | `docker inspect` | Restarts during the step, OOM kills, exit status. Any restart fails the step. |
| `samples[].pg_roundtrip_s` | `SELECT 1` timed | Postgres responsiveness under load. |
| `db.*` | `hypertable_detailed_size`, `approximate_row_count`, `timescaledb_information` | Chunks and chunk interval, table/index bytes, **bytes per row**, database size. Once a compression policy exists (#192), also `db.compression`: bytes before and after compression and the number of compressed chunks, so compressed and uncompressed bytes per row sit side by side. Raw history is never downsampled: compression only. |
| `db.bytes_per_day_raw_at_this_rate`, `ingest.rows_per_day_at_this_rate` | bytes/row × stored rows/s × 86,400 | **Disk-growth math** at the rate measured. |
| `graph.ingest_s`, `tags_per_s` | Oxigraph count of `scale` points after publishing a step's tags | How long the graph takes to absorb new equipment. |
| `graph.triples`, `count_*_s` | SPARQL `COUNT` timed | Graph size and the time of a full scan. |
| `probes[]` | timed GETs through the gateway as the test org's admin, 5 runs, warm median vs. `budgets.json` | **Responsiveness.** Any probe over budget, or not HTTP 200, fails the step. |
| `listener.workers.<n>` | each worker's heartbeat (`service_heartbeats` `mqtt_listener/<n>`, every 5 s) | **Per-worker throughput and CPU** (#233): mean `readings_per_s`, mean/max `cpu_pct` (the worker process's CPU, 100 = one core), and `blocked_s`, the seconds `on_message` waited on a full batch queue. Blocked time with spare CPU means Postgres is the wall; CPU near 100 means add workers. |
| `listener.restarts_delta`, `listener.broker_dropped_delta` | the supervisor's heartbeat (`mqtt_listener`) | Worker or tag-path restarts during the step (any fails it, like a container restart), and the broker's drop counter as the listener saw it. |
| `listener.tag_path` | `mqtt_listener/tags` heartbeat | The tag path's lag on the reading feed and tag messages applied. |
| `tags_storm` (`--tags-storm N`) | tags for N new points published mid-soak; canary lag over the storm | #233's done-when: a tags storm must not push p95 reading lag past 30 s. `graph_s` is how long the graph took to have them all. |
| `rules.<service>.feed` | `reading_feed_consumers` sampled every 15 s | **Rule-daemon misses and lag** (#243). `missed_readings_delta` counts readings pruned from the feed before the daemon read them (more than `BALER_FEED_RETENTION_S` behind) and must be 0. `lag_s_max`/`lag_s_last` show how far behind it ran; still over 30 s at the end of the soak fails the step. |
| `rules.<service>.heartbeat` | `service_heartbeats.detail` | Readings consumed, Cur-mode evaluations (`cur_evaluations`) or rows run (`cur_rows`), and for fault_detector the last His sweep: `sweep_s`, rules, faulted points. |
| `cx_run_s` | creating a 1 h Cx run over site 0 (500 points) and waiting for it | Commissioning verification time. |
| `limiter`, `evidence` | the evidence sampler during the soak and probes, Jaeger after them | What limited the step, and why: see [Reading the limiter](#reading-the-limiter-269). |
| `probes[].trace` | Jaeger's `/api/v3/traces` for the probe's API, over the probe's own time window | Per-span self time of the median request, its share of the request, and the time outside any span (gateway, network). |
| `durability.comparable` | `SHOW fsync / synchronous_commit / full_page_writes` on the server **and** on an ingest-path connection (from inside the listener container) | `true` only if all three are on end to end. A non-durable run is never labelled comparable. |

The ladder adds two rules to the test org, so per-point rule load is realistic: a Cur-mode
`range` rule over every scale point, and a His-mode `stale` rule. Their bounds keep them
from firing, so a fault storm doesn't distort the run.

`crash` runs readings, kills each `--kill` target with `kill -9` mid-run (default:
the `mqtt_listener` container, then `listener_worker` - one worker process inside it, which its
supervisor restarts while the other workers carry on - then `postgres`), brings it back,
drains, and reports `missing_acked`. That is
the number of readings the broker acknowledged that never reached `point_history`. Batching
and group commit are fine; losing acknowledged readings is not.

## Long soak: disk and compression (#245)

The ladder's steps are 15 minutes long, too short for a compression cycle. `ladder.py soak` holds
one point count for hours and answers [#245](https://github.com/jacobnash/Baler/issues/245)'s
question: once compression keeps up, does `point_history`'s disk stop growing at the raw rate, and
do lag, reads, the continuous aggregates and late writes stay fine through compression cycles?

Set the chunking under test in the scale env file **before** `up`, so every service agrees on it
(each keeps the policy in step with its own environment at start, see
[History compression](/history-compression#chunk-interval-and-compress_after-at-high-ingest-rates)):

```sh
# scripts/scale/scale.env (or <SCALE_PROJECT>.env)
BALER_HISTORY_CHUNK_INTERVAL=1 hour
BALER_HISTORY_COMPRESS_AFTER=3 hours
```

`soak` refuses to run on 7-day chunks unless `--allow-default-chunks` is given. It then runs the
generator at `--points` for `--duration` seconds (default 6 h) and records:

| Every | What | From |
|---|---|---|
| `--sample-every` (30 s) | disk: `point_history` total, **hot** (uncompressed chunks) and compressed bytes and chunk counts, before/after compression bytes, WAL, database | `chunks_detailed_size`, `hypertable_compression_stats`, `pg_ls_waldir` |
| | the oldest uncompressed chunk's age past its end, and the **backlog** (chunks old enough to compress that aren't yet) | `timescaledb_information.chunks` |
| | each compression run: duration, chunks, rows (the chunks' inserts while hot), **rows/s** | `job_stats`, `pg_stat_user_tables` |
| | whether a compression run is in progress (polled every 2 s) | `pg_stat_activity` |
| | the 5m/1h aggregates' watermark age; canary lag; restarts | catalog, canary, `docker inspect` |
| `--probe-every` (600 s) | every read probe in `budgets.json` plus its `soak_probes`: history over the last hour and across the hot/compressed boundary, `hisRead(pastWeek)` for 100 and 1,000 points. Rounds that overlapped a compression run are marked | gateway |
| `--late-every` (1800 s) | late data into the newest compressed chunk, over MQTT at the soak's own rate: every point's reading there **replayed** (same ts, new value: a spool or retained replay) and a new reading **backfilled** 1.23 s after it (Windrow's trend backfill). Then each must be stored exactly once, with the new value | generator account |

At the end it compares stored with acknowledged readings over the soak (minus its own backfill),
checks `point_history_5m` against the raw fold over the newest compressed hour, and writes
`results/<run>-soak.json`. `summary` holds the numbers; `status`/`reasons` the verdict.

**Pass** needs all of these (`soak.evaluate_soak`, tested in `tests/test_scale_soak.py`). The
steady phase starts after `compress_after` + 2 chunks + one schedule:

- **Hot window bounded:** hot bytes in the second half of the steady phase at most 1.25× the
  first half's; no chunk uncompressed longer past its end than `compress_after` + chunk + 2 ×
  schedule + the longest run; the backlog not growing.
- **Disk grows at the compressed rate:** total bytes per stored row, between two samples a whole
  number of chunk intervals apart (the same point of the hot sawtooth), at most 2× the measured
  compressed bytes per row.
- **Compression keeps up:** no failed run. `compression_margin` reports median compression rows/s
  over ingest rows/s (one background worker).
- **Ingest:** ≥ 99% stored, no lost canaries, p95 lag under 30 s overall and in the samples taken
  during compression, no growing backlog, no restarts.
- **Reads:** every probe round in budget, and at least one round during a compression run
  (otherwise `inconclusive`).
- **Aggregates:** the 5-minute aggregate equals the raw fold over a compressed hour; watermarks no
  further behind than their offset plus two schedules (20 min for 5m, 2 h 10 min for 1h).
- **Late data:** at least one late round, every replay and backfill stored once.
- At least 2 chunk intervals and 2 compression cycles in the steady phase, or the verdict is
  `inconclusive: soak too short`.

On nash-srv, the real one (6 h at 100k points, after `init`):

```sh
cd ~/baler-scale && git pull
PY=~/.venv-scale/bin/python
$PY -m baler.history_chunks recommend --points 100000 --pg-memory 6g   # the scale stack's postgres cap
printf 'BALER_HISTORY_CHUNK_INTERVAL=1 hour\nBALER_HISTORY_COMPRESS_AFTER=3 hours\n' >> scripts/scale/scale.env
$PY scripts/scale/ladder.py down && $PY scripts/scale/ladder.py up
nohup $PY scripts/scale/ladder.py soak --no-up --points 100000 --duration 21600 --procs 4 \
  --sample-every 60 --probe-every 900 --late-every 3600 > ~/scale-soak.log 2>&1 &
tail -f ~/scale-soak.log
```

Disk at 100k: about 18 GB raw per 1-hour chunk and a hot window up to about 80 GB, plus about
9 GB/day compressed at 5 B/row. Keep `--min-free-gb` (default 5) where it is; the soak stops
(`inconclusive`) rather than fill the disk. Like `run`, it watches the disk holding Docker's data
root (`docker info --format '{{.DockerRootDir}}'`), which on nash-srv is a separate disk from the
checkout's. It falls back to the checkout's disk, with a warning, only when that root can't be
read or isn't visible from the host. Raise `SCALE_MEM_POSTGRES` if the box has the
memory: the sizing rule wants a chunk in 25% of it.

### Reads at scale: paging (#244)

nash-srv's 100k step (commit `c36aec3`, ingest stopped) showed where the read time went:
`read?filter=point` 15.9 s (33 MB: building records 7.6 s, encoding 6.1 s), `readAll(equip)` 15.0 s
(9.4 s of it describing points), `/ops/status` 3.4 s (one scan of the last hour of `point_history`,
36M rows). With no paging, faster queries couldn't fix those: the responses held every point.

The fix makes each request's cost follow its page, not the graph or the history:

- **Paged reads.** A Haystack filter `read` returns at most `limit` records, or `BALER_READ_LIMIT`
  (1000) when the request names no limit, plus meta `after` to read on
  ([Haystack API](/haystack-api#reading-large-graphs-pages)). `/ingest/his` describes and reads at
  most `seriesLimit` points (`BALER_HIS_SERIES_LIMIT`, 1000), plus `after`
  ([Query](/his-query#many-points-pages)). The pages are keyset pages on the entity id. The UI tree and
  `haystack_client.read` follow `after` to the end.
- **The match no longer decodes every candidate.** The compiled filter dropped nested-Dict nodes with
  `STR(?s)` and non-IRIs with `isIRI(?s)`. For each candidate, that's a dictionary lookup or term
  decode in Oxigraph: 1.1 s of a 1.2 s `point` match at 100k. `match_entities` now drops them in
  Python, with the same result.
- **`/ops/status` reads `point_registry`** (#243), not an hour of history. Only points whose coarse
  `last_ts` sits within `REGISTRY_GRANULARITY_S` of the hour boundary are checked against
  `point_history`, one primary-key probe each. The count is exact.
- **The Cx inventory reads only the project's equipment.** It used to read every `hasPoint` triple
  in the graph before scoping.
- **Site membership is walked from the sites**, not backwards from every record on the page. That
  walk was 0.5 s of a 1000-record page even in a graph with no Site.

- **No QoS 0 subscriptions left.** Both daemons read `reading_feed`, so the broker fans each
  reading out to the listener only. The listener appends each committed batch to the feed in
  the same transaction. That's one more INSERT per batch, built server-side from the staging
  table: about 5 points of Postgres CPU at 25k, including `point_registry` upkeep and the
  daemons' reads.
- **fault_detector is idle-cheap.** At 25k it evaluated 3.9M Cur-mode rule checks in the soak,
  a dict lookup each. The His sweep (one `GROUP BY` per stuck window, registry candidates for
  stale) took 0.8 s, against 77 s before.
- **Misses are visible.** Checked live: with `BALER_FEED_RETENTION_S=20`, `fault_detector`
  was stopped for 60 s at 2,000 readings/s. The listener logged `fault_detector MISSED …`
  per prune, and `reading_feed_consumers` counted 80,840 readings in 137 batches. The
  Fault detection card on `/ops/status` went degraded ("missed 80840 reading(s)…").
- **The next wall in fault_detector is the quality sweep** ([#183](https://github.com/jacobnash/Baler/issues/183)'s

  point in Python. At 25k it read 1.3M rows in 10.5 s; a 25k stack with a full hour of

  (1 GB cap) once a full hour of 25k-point history existed. It now reads 150 points at a
  time, and its duration is in the heartbeat (`quality.sweep_s`), but it still has to become
  incremental.

Batched writes cost almost nothing to make durable. At 1,000-row batches, `synchronous_commit=on`
measured 17–25k rows/s against 15–21k for `off`; single-row writes pay the fsync (about 1.3×).

### Listener scale-out (#233): limiter removed, next limiter exposed

nash-srv's 100k step (`20261108T233336Z`, c36aec3) found the first data loss: one listener
process stored 14,921 of 20,000 readings/s (73.9%) at about one core of its 1.5-CPU cap, and
the broker dropped 4.74 M messages. One process is one GIL. #233 runs the listener as
`BALER_LISTENER_WORKERS` processes on the shared subscription `$share/baler/fbf/#` (see
[Architecture](/architecture)), moves tags off the readings path, and makes overload counted.

**Local capacity**, `listener_bench.py` (300,000 readings queued at the broker, then drained;
20,000 points; durable commits). Dev VM, 4 CPUs shared with three other agents' stacks: host
load 9-13 throughout, so every process got well under a core. Read these as lower bounds and
for their shape, not as nash-srv numbers.

| Code | Workers | Stored/s | Per worker | Worker CPU % (each) | Batcher writing % | Postgres CPU % | Missing |
|---|---|---|---|---|---|---|---|
| this branch, before the registry fix | 1 | 10,579 | 10,579 | 67 | - | - | 0 |
| | 2 | 14,353 | 7,176 | 45, 46 | - | - | 0 |
| | 3 | 9,227 | 3,076 | 22, 21, 20 | - | - | 0 |
| | 4 | 11,648 | 2,912 | 23, 19, 22, 21 | - | - | 0 |
| + registry upsert locks only rows it moves | 1 | 11,295 | 11,295 | 58 | 85 | 26 | 0 |
| | 2 | 14,167 | 7,083 | 35, 35 | 96, 97 | 35 | 0 |
| | 3 | **18,232** | 6,077 | 29, 27, 29 | 71-77 | 32 | 0 |
| | 4 | 17,091 | 4,273 | 21 each | 67-73 | 34 | 0 |

- **Limiter removed:** the single process. Two workers store 1.25-1.3x one, three 1.6x, on a
  host with no spare core to give them. No worker ran out of CPU (≤ 58%), and none blocked on
  a full queue.
- **First limiter exposed, and fixed:** `point_registry`. Every batch upserted every point it
  carried with `ON CONFLICT DO UPDATE ... WHERE <moved by 30 s>`, and Postgres locks the
  conflicting row to commit even when the WHERE skips the update. Workers' batches share most
  points, so they queued on each other's registry rows (`Lock transactionid` in
  `pg_stat_activity`): 3 workers stored *less* than 2. The upsert now pre-filters with an
  unlocked anti-join and only locks rows it actually moves.
- **Next limiter:** the `point_history` upsert in Postgres. With 4 workers, sampling
  `pg_stat_activity` every 200 ms found the `INSERT INTO point_history ... ON CONFLICT` active
  in 131 of 189 samples, the registry upsert in 16, `COPY` in 11, and the feed's advisory lock
  waited on in 3. Each worker's batcher is busy writing 70-97% of the time at ≤ 30% CPU: the
  batches wait on Postgres, not on Python. Here that is host CPU starvation (Postgres shows
  ~35% of a core while ~1.2 backends are runnable); on nash-srv's 12 threads it's the next
  thing the ladder will find, so `ingest.stored_rps` with more workers than that adds nothing
  is the signal to look at the write path (narrow row, #245) or Postgres's CPU cap.

**Tags storm during readings** (20,000 new points' tags plus 2,000 equips published in 4.5-5 s,
while 10,000 points report every 5 s; same host, same broker and Postgres):

| Code | Graph had them all after | Tags/s into the graph | Reading lag p95 before → during |
|---|---|---|---|
| main c36aec3 (inline, one process) | 149 s | 134 | 1.0 s → **141 s** (readings fell to ~30/s) |
| this branch, 2 workers | 7.4 s | ≥ 2,700 (bounded by the publisher) | 1.0 s → **1.0 s** |

Tags now ride their batch into the reading feed (no Oxigraph call in `on_message`), and
`tag_ingest` applies each poll's tags in about five Oxigraph requests: one `INSERT DATA`, one
update per link direction, two reads and a write for classification.

**Overload is explicit:** each worker counts the seconds `on_message` blocked on a full queue
(`blocked_s` in its heartbeat); the supervisor reads the broker's drop counter and logs
`BROKER DROPPED n message(s)`, puts it in the `mqtt_listener` heartbeat, and `/ops/status`
shows ingest degraded for an hour; the tag path's lag is a reading-feed consumer's lag. The
broker's per-client queue is bounded at 500,000 messages or 64 MiB of payload, whichever comes
first (~550 B of broker memory per queued reading, measured), and per client, so N workers
buffer N times that. Queued messages don't survive a broker crash: Windrow's spool covers the
uplink, and at steady state each worker's queue is under one batch. A test run that left the
pre-#233 session unattended for a few minutes at 2,000 readings/s filled exactly 500,000 and
dropped the rest, which is what the limit is for, and why the supervisor now retires sessions
no worker resumes.

What the proxy does **not** show, and the nash-srv run has to:

- Compression at the real chunk size. Runs here took under 2.3 s, so only 1 of 8 probe rounds and
  none of the 15 s lag samples overlapped one (`lag_p95_during_compression_max` is empty). At 100k
  points a 1-hour chunk is about 72 M rows: at nash-srv's earlier ~33,000 rows/s that would be 36
  minutes per hour in one worker, so whether it keeps up there is exactly the open question
  (`compression_margin` answers it).
- The 1-hour aggregate: with its 1-hour end offset its watermark never moved inside this soak.
- Read probes at 100k points, which the ladder already shows are the first wall (above).

Earlier local finding, from the same work: a 2,000-point overwrite batch into compressed chunks
failed TimescaleDB's 100,000-row decompression cap and would have put mqtt_listener into a
restart loop; writers now lift that cap per transaction
([History compression](/history-compression)).

### Disk growth

At 1M points every 5 s, that's 200,000 rows/s, or 17.3 billion rows/day. Bytes per row comes
from `db.bytes_per_row` in each result (table plus index, uncompressed). On the first local
runs it was 228–265 B/row (241 at 1k points, 265 at 25k). That works out to about **4.2 TB/day
raw** at 1M points, which is why
native compression ([#192](https://github.com/jacobnash/Baler/issues/192), under [#221](https://github.com/jacobnash/Baler/issues/221)) and a narrower row matter. Raw rows are kept, never downsampled. Fill in compressed bytes per row from `db.compression` once #192 lands.

For sizing a deployment from these results (disk, chunk settings, listener workers, servers), see
[Deployment profiles and sizing](/deployment-profiles) and `python -m baler.sizing`.
