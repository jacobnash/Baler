# Manual, passive and active steps

One procedure can mix traditional and automated commissioning (Baler#275).
Each step says how it can be judged, and each test run picks one method per
step. A CxA can do one step by hand and the next one automatically, or
start a step manually and automate it later, all in the same procedure.

| Method | The step's verdict comes from |
|---|---|
| `passive` | its criteria, judged over history (the default; every procedure written before this is passive) |
| `manual` | a person: pass, fail or N/A, with a note, attachments and an optional witness |
| `active` | a Cx 9 active test on the equipment (`"active": {"kind": "command_response"}`) |

```json
{"name": "AHU functional", "kind": "functional", "equip_class": "Air_Handling_Unit", "steps": [
  {"id": "visual", "title": "Belts, filters, access doors", "methods": ["manual"], "witness_required": true},
  {"id": "sat", "title": "Supply air plausible", "methods": ["passive", "manual"],
   "criteria": [{"range": {"min": 40, "max": 110, "unit": "F"}, "point_class": "Supply_Air_Temperature_Sensor"}]},
  {"id": "fan", "title": "Fan status follows command", "methods": ["active"], "active": {"kind": "command_response"}}
]}
```

- A step whose only method is manual needs no machine criteria.
- `POST /cx/procedures/{id}/runs {"methods": {"sat": "manual"}}` chooses
  a method per step for that run. A step you don't name uses its first
  method. The choice is stored on the run.

## Manual results

`POST /cx/test-runs/{id}/manual-results` (operator) records one result:

```json
{"equip_uri": "urn:equip:...", "step_id": "visual", "status": "pass",
 "note": "belts tight, filters new", "witness": {"name": "Pat Owner", "org": "Owner"},
 "attachments": [{"filename": "belts.jpg", "media_type": "image/jpeg", "data": "<base64>"}],
 "client_id": "web:3f2c…", "observed_at": "2026-11-09T14:05:00Z"}
```

- **Who:** the result is always recorded as the signed-in person: their
  sub, email, display name and role, taken from their token. There is no
  field for anyone else, and API keys are refused. Only the person who
  recorded a result can edit it (`PATCH /cx/manual-results/{id}` with a
  `reason`). Every edit keeps the previous version in `history`.
- **When:** `recorded_at` is the server's clock. `observed_at` is when the
  person checked, and can be up to 14 days back for an entry made offline.
- **Attachments:** up to 5 files of 5 MB each (images, PDF, text), stored
  with their sha256. `GET /cx/manual-attachments/{id}` returns the file.
- **Witness:** a name, organization and role. Witnesses often have no Baler
  login. `witness_required` on the step keeps it inconclusive until a
  result names one.
- **Offline:** the Commissioning page saves each entry on the device first
  and sends it when there is a connection. Because the entry carries a
  `client_id`, a resend is stored once (the second send answers 200 with
  the stored row). An entry the server refuses stays on the device with
  the reason, and is not resent.

## One verdict, three sources

A step's `status` is the verdict of the method the run chose, so manual,
passive and active results feed the same phase gates, issues and reports.
Each step also records:

- `method`: which method decided the status;
- `machine_status` and the `criteria`: the data's verdict. It is always kept
  and never overwritten by a typed value;
- `manual`: the current manual result (the latest by observed time). Older
  results stay on the record;
- `active`: the newest active run on the equipment that started after the
  test run did. The run itself goes through every Cx 9 safeguard, which is
  unchanged;
- `contradiction`: set when a person's pass or fail disagrees with the
  data's pass or fail. The report shows both values.

The run's status updates when a result is recorded, or when the run, the
gate, the coverage or the report is read after an active test finishes.

## Issues

Manual and active verdicts, and disagreements, are Cx results on the
equipment. They open and close issues like any check:

| Result | When |
|---|---|
| `manual:<procedure>/<step>` | a manual step's result; a fail opens an issue |
| `active:<procedure>/<step>` | an active step's result; a fail opens an issue |
| `contradiction:<procedure>/<step>` | fail while a person and the data disagree, pass once they agree |

Closing works as for any check-linked issue:

1. The issue becomes `ready_for_retest`, either because a pass resolves it
   or because someone claims the fix.
2. A pass whose check happened after that (its `observed_at`) is the
   retest.
3. A person closes the issue. The close cites the test run in
   `closed_run`, and the person in `closed_by`.

`closed_by` is now recorded for every issue close.

## Coverage

`GET /cx/projects/{id}/coverage` returns one row per equipment class. It is
also in the project report and on the Commissioning page, and it is based
on each active procedure's latest test run:

- **in scope:** equipment of that class in the project;
- **sampled:** the equipment the procedures cover;
- **tested:** at least one step judged pass or fail;
- **passed:** every judged step passed, and none is inconclusive;
- **per method:** tested manually, passively or actively. Automatically
  means passively or actively;
- **witnessed:** at least one manual result names a witness.

For example: "220 of 220 tested: 220 automatically, 12 manually, 12
witnessed".

## The standard active-test library

`GET /cx/active/library` lists the standard active tests, stored as data
in `commissioning/test_library.py`:

| id | Equipment | What it proves |
|---|---|---|
| `vav_reheat` | VAV | The damper opens and airflow rises by at least 50 cfm; the reheat valve opens and the discharge air warms by at least 5 F |
| `ahu_basic` | AHU | The supply fan's status follows its command; the supply air comes within 2 F of a setpoint stepped 3 F lower |
| `chw_loop` | Chilled-water system | The pump's status follows its command; the chilled water supply comes within 1.5 F of a setpoint stepped 2 F lower |

**What each test states, written against Brick classes:**

- the equipment class it applies to;
- its steps: the writes, which are absolute or an offset from the latest
  value, and the expectations: equals / min / max, near the setpoint it
  wrote, or a rise or fall from the latest value;
- its **safety limits**: the range every commanded value must stay
  within, and the longest any step may hold (never more than Cx 9's 60
  min);
- its **expected result**, in words, for the report.

**Planning a test:** send
`POST /cx/projects/{id}/active-runs {"kind": "library", "test": "ahu_basic", ...}`.

- The test is compiled for that equipment against its latest values, so
  the dry run lists the exact numbers that will be written and expected.
- If a resolved value falls outside the test's limits, the plan is
  refused.
- From there the run is a Cx 9 active run like any other: admin only,
  `BALER_CX_ALLOW_WRITES`, a window, expiring writes, typed confirmation,
  guaranteed relinquish, sweeper and kill switch, all unchanged.

**Judging a procedure step:** a step with
`"active": {"kind": "library", "test": "ahu_basic"}` is judged by the
newest such run on its equipment.

## Fleet active runs

A fleet run is one active test across many pieces of equipment in one
window, such as every terminal unit overnight. It is a scheduler on top of
Cx 9, not a second way to write: each piece of equipment is its own
ordinary active run (`fleet_id` set). So **every #45 safeguard still
applies to every write**: `BALER_CX_ALLOW_WRITES`, admin only, the window,
writes that expire, priority 8 as `cx:<run id>`, relinquish after each step
and after each run, the sweeper, the kill switch, and the before-state
captured before each unit's first write.

**Planning:** send `POST /cx/projects/{id}/fleet-runs` (admin) with the
members, the test and the limits:

| Field | Default | Meaning |
|---|---|---|
| `equip_uris` / `equip_class` / `retest_of` | | The members: a list, every unit of a Brick class (subclasses match), or the units that **failed** in a finished fleet run (retest-failures-only, with that fleet's test) |
| `kind`, `test`, `response_minutes` | `command_response` | `command_response`, or `library` with a test id from the library above |
| `concurrency_per_system` | 1 | At most this many units of one system run at once. A unit's system is the equipment that feeds it (`brick:feeds` / `brick:isFedBy`); units nothing feeds share one system |
| `max_concurrent` | 10 | At most this many units at once, across all systems |
| `stagger_seconds` | 30 | The least time between two units starting |
| `max_failures` | 3 | The fleet stops by itself once this many units have failed |

The dry run commands nothing. It returns:

- every member with its steps, its system and its slot (the earliest time
  it may start, worked out with the limits and the stagger);
- **every write across the fleet**: equipment, point, value, priority,
  hold, not-before and expiry;
- the units that can't take the test, and why (`skipped`);
- `plan_hash`, a sha256 over the fleet id, the test, the window, the
  limits and every member's steps and slot.

A fleet that doesn't fit the window is refused.

**Confirming:** send `POST /cx/fleet-runs/{id}/confirm {"confirm": "<plan_hash>"}`.
The typed confirmation is the plan's hash, not the fleet's id. When it
arrives, the stored plan is hashed again and every member is checked
against today's inventory: it must still be in your view and its steps
must still validate (its points still writable, its command/status pairs
the same). If anything changed, the answer is 409 and the fleet must be
planned again, which gives a new hash. The switch, the admin role and the
window are checked exactly as for one run.

**Running:** members start in plan order, never before their slot, and
never past the concurrency limits or the stagger. Before each start the
coordinator checks the switch and the fleet's abort flag again. A member
fails if any step fails or its run fails; aborted and inconclusive members
don't count.

**Stopping:** the fleet stops when:

- the failure threshold is reached (`stopped`);
- someone calls `POST /cx/fleet-runs/{id}/abort` (operator) or the kill
  switch `POST /cx/active/kill` (`aborted`);
- `BALER_CX_ALLOW_WRITES` is switched off (`stopped`).

Then no unit starts again, every running unit stops at its next check (a
member also checks its fleet, before every step and between polls), and
every level the fleet's units hold is relinquished at once. When they have
all stopped, the levels are relinquished again. The units that never ran
are listed as `not_run`.

**Crashes:** a unit's run id is saved on the fleet before the unit is
created, and the coordinator saves a heartbeat on every pass. On restart,
fleets that were confirmed or running are marked failed, along with their
units, and the sweeper relinquishes every level they held, using only this
saved state. While the process is running, the sweeper does the same once a
minute: for any fleet that has stopped, finished or been aborted, and for
any whose heartbeat is more than 3 minutes old (its coordinator died).

**Retesting failures:** once the contractor has fixed the failed units,
plan `{"retest_of": "<fleet id>", ...}`. Only the failed units are
planned, so nothing else is commanded. It is a new plan with a new hash.
On the Commissioning page, use the **Retest failures** button on a
finished fleet.

## Scheduled retests

A scheduled retest repeats a fleet run, for example every season. It runs
only under an admin's approval that names its scope and its window, and
**approving never turns writes on**.

**Proposing:** send `POST /cx/projects/{id}/active-schedules` (admin). The
proposal names:

- **the scope**: the equipment (`equip_uris`, or every unit of
  `equip_class`, frozen as a list when proposed), the test (`kind`,
  `test`, `response_minutes`), the fleet limits, and `mode`. In `all` mode
  every unit is retested each window. In `failures` mode only the units
  that failed in the schedule's last run are retested;
- **the window**: `first_window_start`, then every `every_days` days, each
  `window_minutes` long (at most 8 hours), until `valid_until` (at most 400
  days ahead).

Nothing runs yet. The answer has an `approval_hash` (a sha256 of the scope
and the window) and a dry run of the next window, listing every write.

**Approving:** send `POST /cx/active-schedules/{id}/approve {"confirm": "<approval_hash>"}`.
This must be an admin, signed in as a person: API keys are refused. The
approved scope and window are kept as an envelope, separate from the
schedule.

**Narrowing only:** after approval, `PATCH /cx/active-schedules/{id}` can
only narrow the schedule inside the envelope. It can:

- drop equipment;
- shorten the window, or end the approval sooner;
- lower `concurrency_per_system`, `max_concurrent` or `max_failures`, or
  lengthen the stagger;
- go from `all` to `failures`.

Anything else is refused with 409: more equipment, another test, a longer
or moved window, a later `valid_until`. Those need a new schedule and a
new approval.

**Each window:** once a minute the scheduler looks at approved schedules.
For a window that has started and not been handled yet:

- If `BALER_CX_ALLOW_WRITES` isn't `1` at that moment, or no point_write
  route is configured, the window is **skipped**, and the skip is audited.
- Otherwise a fleet run is planned afresh from the current inventory, as
  the approver can see it. It is checked against the envelope once more,
  then confirmed in the approver's name, recorded with `schedule_id`, and
  run like any other fleet run. Every #45 safeguard applies to each write.
- A window is handled once, whether it ran or was skipped. A window
  doesn't start while the schedule's previous run is still going.

**Expiry and revoking:** once `valid_until` passes, the schedule is
`expired` and stops scheduling. `POST /cx/active-schedules/{id}/revoke`
(operator, the safe direction) stops it at any time. If it has a fleet run
going, that run is stopped and every level it holds is relinquished.

**Audit:** each step is a `cx_events` row: `active_schedule.propose`,
`approve`, `edit`, `revoke`, `run` (with the fleet run, its `plan_hash` and
the approval hash), `skip` (with the reason) and `expire`.
