title: Haystack API
---

Baler serves the standard [Project Haystack HTTP API](https://project-haystack.org/doc/docHaystack/HttpApi),
so tools that already speak Haystack can use it without changes. SkySpark, Haxall's haystack
connector, nhaystack's client side, pyhaystack, phable and openhay's `hay` all work this way:
point the tool at Baler instead of a SkySpark host.

```
https://<your-host>/api/<project>/<op>     # SkySpark layout
https://<your-host>/api/<op>               # Haxall layout, same thing
```

`<project>` is accepted so SkySpark-shaped URLs work, but it doesn't scope anything yet.

## Logging in

Use your normal Baler email and password. Haystack clients run the standard HELLO →
SCRAM-SHA-256 handshake. Your password is never sent: it's checked against the same password hash
`POST /auth/login` uses, so there's nothing to reset and no second password to manage. The
handshake ends with a normal session JWT as the Haystack `authToken`.

You can also skip SCRAM and send any token the gateway accepts (a session JWT or an API key from
`POST /auth/api-keys`) as either:

```
Authorization: Bearer <token>                 # OAuth / modern API style
Authorization: BEARER authToken=<token>       # Haystack style
```

Read-type ops (`about`, `read`, `nav`, `hisRead`, `watch*`) need the `viewer` role.
`hisWrite` needs `operator`. Login attempts are rate-limited per IP at the gateway.

## Try it

With [openhay](https://github.com/jacobnash/openhay)'s `hay` CLI:

```bash
hay read http://localhost:8080/api/demo "point and temp" --user admin@acme.example --password change-me
hay his  http://localhost:8080/api/demo @urn:point:windrow~2Fmock-ahu-1~2FanalogValue~2C1 yesterday --to csv
```

From Python (`pip install -e ".[haystack]"` installs openhay):

```python
import openhay as oh

c = oh.Client("http://localhost:8080/api/demo", user="admin@acme.example", password="change-me")
for rec in c.read("ahu"):
    print(rec["id"], rec.get("dis"))
his = c.his_read(c.read("temp and sensor", limit=1)[0]["id"], "yesterday")
```

openhay's `read` returns the first page only, 1,000 records by default. For more, see
[Reading large graphs](#reading-large-graphs-pages).

## What a record looks like

Records come from the same entity graph everything else reads:

| Haystack tag | where it comes from |
|---|---|
| `id` | the entity URI. Characters Haystack ids don't allow are escaped as `~XX`, e.g. `@urn:point:windrow~2Fahu-1~2FanalogInput~2C1` |
| markers (`temp`, `sensor`, …) | `haystack:hasTag` facts, as written by ingest and the Haystack puller |
| other tags (`dis`, `kind`, …) | `haystack:<tag>` values |
| `point` / `equip` | the kind of URI |
| `equipRef` | `brick:isPointOf` in the graph, not the original source's ref, so it always resolves here |
| `brickClass` | the Brick class mapping assigned |
| `spec` | the most specific `ph` Xeto spec the record fits (`@ph::Ahu`, `@ph.points::ZoneAirTempSensor`): from its own markers plus those its Brick class implies, so Brick-only records are typed for Xeto clients too. A stored `spec` (Haystack 4 import) is kept as-is. |
| `curVal`, `unit`, `his`, `mod` | the newest sample in the historian |

Filters work exactly like the [Query page](/his-query): a name matches as a Haystack marker,
a Brick class (`Air_Handling_Unit`) or a Brick tag word. So `read ahu` also finds AHUs that
never had a Haystack `ahu` tag. Tag paths (`point and equipRef->ahu`,
`equipRef->siteRef->dis == "HQ"`), units (`area > 1000ft²` matches only `ft²`, with no
conversion), date, time and Uri literals, and `^symbol` terms all work.

## Who sees what

Reads are scoped to the caller's sites once sites own data. See
[Multi-Site](/multi-site#who-sees-which-data). Anything out of scope reads as if it didn't exist.

## Reading large graphs: pages

A filter `read` answers a page at a time. With the spec's `limit` it returns at most that many
records; without one, at most `BALER_READ_LIMIT` (default 1000). A graph smaller than that never
notices: its reads come back exactly as they always did, in one grid with no extra meta.

A page that stops short of the end says so in its grid meta:

| meta | |
|---|---|
| `incomplete` | why the grid is short, e.g. `limit of 1000 reached; pass after to read on` |
| `limit` | the page size used |
| `after` | the id of the last record the page covered |

The same page also says so in its HTTP headers, for clients that hand their caller only the rows:

| header | |
|---|---|
| `X-Baler-Incomplete` | the meta's `incomplete` text. Set on any grid whose meta has `incomplete` |
| `X-Baler-After` | the meta's `after`, e.g. `@urn:point:fbf~2Fahu-3~2Fsat` |
| `X-Baler-Limit` | the meta's `limit` |
| `Link` | `<?filter=point&after=%40urn...>; rel="next"`: a GET of the next page, relative to the request's own path ([RFC 8288](https://www.rfc-editor.org/rfc/rfc8288)) |

They're listed in `Access-Control-Expose-Headers`, so a browser client on another origin can read them.

### How a standard Haystack client pages

The Haystack spec's `read` op takes a `limit`, and a grid that stops short may carry grid meta
`incomplete`. It has no way to ask for the next page. `after` is Baler's extension to fill that gap:

1. Send the `read` as usual: `filter`, and `limit` if you want a page size other than the server's.
2. If the response's grid meta has `after`, send the same `filter` (and `limit`) again with `after`
   set to that Ref, as a request-grid column (POST) or a query parameter (GET).
3. Repeat until a page comes back without `after`. That page is the last. A page can be empty, with
   no `after`, when the previous one ended exactly on the last match.

Servers that don't page ignore `after`, and Haxall never sets the meta, so a client that follows
`after` works against any server: against one that doesn't page, the first response is the whole read.

```python
import openhay as oh

c = oh.Client("http://localhost:8080/api/demo", user="admin@acme.example", password="change-me")
recs, after = [], None
while True:
    req = {"filter": "point"} | ({"after": after} if after else {})
    page = c.call("read", oh.Grid.from_rows([req]))
    recs += page.rows
    after = page.meta.get("after")
    if after is None:
        break
```

```bash
curl -i -H "Authorization: Bearer $TOKEN" "$BASE/api/read?filter=point"
# HTTP/1.1 200 OK
# X-Baler-Incomplete: limit of 1000 reached; pass after to read on
# X-Baler-After: @urn:point:fbf~2Fahu-3~2Fsat
# Link: <?filter=point&after=%40urn%3Apoint%3Afbf~2Fahu-3~2Fsat>; rel="next"
curl -H "Authorization: Bearer $TOKEN" "$BASE/api/read?filter=point&after=@urn:point:fbf~2Fahu-3~2Fsat"
```

Pages come in id order and are keyset pages: page *n+1* starts after the last id of page *n*, not at
an offset. So a walk stays correct while records are added or removed. A record that exists for the
whole walk is returned exactly once. One added or removed during the walk may or may not appear.
Every page costs about the same however far in it is.

### What a client that doesn't page sees

It gets the **first page only**: the first 1,000 records in id order (or `limit`, if it sent one),
with no error. The grid's meta says `incomplete`, and the headers above say the same, but a client
that returns only the rows drops both. Its caller can't tell a 1,000-record answer from a complete
one. On a site with 1,000 matches or fewer nothing changes: one grid, no extra meta.

| client | follows `after`? |
|---|---|
| Equipment page (`ui/app.js` `haystackRead`) | yes |
| `baler.haystack_client.HaystackClient.read` (Haystack puller, Ops → Sources, `baler_fn`, the notebook image) | yes, unless given a `limit`; the result carries `.after`/`.incomplete` |
| `baler_fn.connect().read` / `read_df` | yes, unless given a `limit`; `read_page` for one page |
| `baler.openhay_paging.read` / `openhay_paging.Client` | yes: Baler's wrapper around openhay |
| openhay `Client.read` | **no**: first page, meta dropped. Use `openhay_paging`, or `call("read")` as above |
| phable `read_all` (the notebook's library) | **no**: one request, first page; the grid's `meta` has `after`, which `to_pandas()` drops. `baler_fn.phable_read_all` follows it |
| Windrow's Haystack source pointed at a Baler | **no** (openhay's `read`); see below |
| SkySpark/Axon `read`/`readAll` via a connector, other clients | no, unless they follow `after` themselves |

With openhay, Baler's wrapper is a drop-in until openhay follows `after` itself:

```python
from baler import openhay_paging

c = openhay_paging.Client("http://localhost:8080/api/demo", user="admin@acme.example", password="change-me")
recs = c.read("point")             # every page; recs.after is None
page = c.read_page("point", 500)   # one page; pass page.after to read_page for the next
```

If a client can't be changed, there are two ways to give it a complete answer:

- **Send a `limit`** as large as the graph. The read comes back in one grid.
- **Set `BALER_READ_LIMIT=0`** for the whole install: every read without a `limit` is one unbounded
  grid, as before #244. That's what reads at scale can't afford: at 100k points one grid was 33 MB
  and took 16 s to build and encode ([Scale test](/scale-test#reads-at-scale-paging-244)).
  Raising it (say, to 20000) is the middle ground for a site that knows its size.

Reads by `id`, `nav`, `watchSub`/`watchPoll` and `hisRead` aren't paged.

## Formats

Requests can be `GET` with Zinc-encoded query params, or `POST` with a grid in Zinc, JSON (Haystack 3
or Haystack 4/Hayson) or Trio. Responses follow `Accept`: Zinc by default, plus `application/json`,
`text/trio` and `text/csv`. A JSON request gets JSON back in the same flavor, so older Haystack 3
clients keep working.

## Commanding points (pointWrite)

`pointWrite` with a `level` (1-17) commands a real BACnet point. A `val` of `null` relinquishes that
level. Level 17 is the default the point falls back to when every other level is empty (BACnet's
relinquish-default): it can be set but not relinquished. It works the way an operator's command at a controller does: a write at 8 overrides the
controller's own logic until it's released.

- **Writable points:** Windrow tags BACnet setpoints and commands (analog, binary and multi-state
  *output*/*value* objects, never sensors) as `writable`. Only those accept a write.
- **Routing:** the write goes to the Windrow instance that owns the point. That instance must run
  with `--site-id`, which is how it advertises its command channel. The command travels over that
  site's broker-ACL-protected MQTT channel.
- **Confirmation:** a successful response means the controller accepted the BACnet WriteProperty.
  Nothing is merely queued.
- **Offline sites:** if the site is offline, the call fails after 10 seconds. The command expires
  30 seconds after it was sent, and the site refuses it after that, so it can never apply a stale
  setpoint when it reconnects.
- **Timed overrides:** a level-8 write with a `duration` (`30min`, `2h`) is relinquished
  automatically when it runs out; without one it stays until released, as in Haxall. The array's
  `expires` column shows the time left.
- **Reading the array:** `pointWrite` without a `level` returns the 17-level array of what Baler
  has commanded (`level`, `levelDis`, `val`, `valDis`, `who`, `expires`, as Haxall returns it).
  The controller's own array can also hold other writers' levels.
- **Units:** a Number's unit is not converted. Send the value in the point's own unit.
- **Roles:** writing needs the `operator` role. Haystack clients POST pointWrite for reads too, so
  reading the array also needs `operator`.

## Deliberately unsupported

- **`invokeAction`** answers with a Haystack error grid (HTTP 200, `err` meta) that says it isn't
  supported, and `ops` doesn't list it. In SkySpark and Haxall an action is an Axon expression in a
  record's `actions` grid. Baler records define no actions and Baler has no Axon to run one. To
  command a point, use `pointWrite`.
- **A Symbol as a comparison value** (`kind == ^elec`) is a filter parse error. Haystack's filter
  grammar doesn't include it. A bare `^hot-water` term works and means `hot and water`.

## Ops, checked against Haxall

`hisRead` takes every range the spec defines (`today`, `yesterday`, a date, a date range, two
dateTimes, or one dateTime meaning "until now"), and the **batch** form (meta `range`, one `id` row
per point, returning `ts, v0..vN`). `hisWrite` takes the batch form too (a `ts` column plus one
column per point, each naming its point with an `id` in the column meta). `close` ends the session:
the token is refused by `/api` at once and by the gateway, on every API, within 30 seconds. `ops` returns the
Haystack 4 op defs. Each of these is a column in the CI conformance matrix, run against Haxall
as the reference ([Haystack conformance](/haystack-conformance)).
